## 1. 产品愿景与目标

### 1.1 一句话描述

AgentX 是一个**对话式 AI 工作助手**。用户打开一个聊天窗口，对 Master 说出想做的事，Master 自动调度背后专业 Agent 团队完成工作，结果直接呈现在对话中。

**核心理念**：用户不需要知道有几个 Agent、各自叫什么名字。用户只需要说"帮我做XX"，结果就出来了。

### 1.2 产品形态

只有两个页面：**登录页** + **对话页**。所有功能发生在对话中。

### 1.3 核心价值主张

| 优先级 | 场景 | 现状 | 使用 AgentX |
|--------|------|------|-------------|
| P0 | 达人筛选 | 手动刷多平台，Excel 记录 | 对 Master 说一句话 → 结果出现在对话中 |
| P0 | 达人建联 | 手动写私信，回复率低 | Master 自动生成个性化话术 |
| P0 | 多 Agent 协作 | 一个人做所有事 | 一句话驱动整个 AI 团队 |
| P1 | 内容脚本策划 | BD 自己写脚本 | Master 自动策划，可迭代修改 |
| P1 | 竞品分析 | 人工盯竞品 | Master 自动搜索+分析+输出报告 |
| P1 | 物流跟踪 | 手动查快递 | 一句话查所有物流状态 |
| P2 | 复盘报告 | 手动整理数据 | 一句话生成完整复盘报告 |

### 1.4 目标用户

**MVP 核心用户**：电商商务人员（达人 BD），负责品牌 KOL/达人全流程管理。

**扩展用户（第二、三期）**：电商运营专员、独立电商创业者。

## 2A. RAG 检索增强生成系统（v3.2 增强版）

### 2A.1 为什么需要 RAG

大语言模型的知识截止于训练日期，且无法访问企业内部数据。RAG（Retrieval-Augmented Generation）在 LLM 生成回答之前，先从企业知识库中检索相关文档，将检索结果注入 LLM 的上下文，使回答基于真实数据而非幻觉。

**在 AgentX 中，RAG 解决三个核心问题：**

| 问题 | 没有 RAG | 有 RAG |
|------|----------|--------|
| 行业实时数据（达人粉丝量变化、竞品动态） | 模型回答基于训练时的旧数据 | 从最新抓取的知识库中检索，回答基于当前数据 |
| 企业内部资料（品牌手册、达人合作规范） | 模型不知道你的品牌调性和合作标准 | Agent 自动根据你的品牌资料生成符合标准的输出 |
| 历史经验（上次合作怎么做的、效果如何） | 完全遗忘 | 自动检索相似历史任务的经验，供 Agent 参考 |

### 2A.2 完整检索链路（v3.2）

### 2A.3 架构：三层数据注入

```
用户请求
  │
  ▼
┌─────────────────────────────────────────────────────┐
│  DataInjector（Agent 上下文自动注入器）                │
│                                                      │
│  执行前注入：                                          │
│  Layer 1: 公司基础资料（PostgreSQL，静态数据）          │
│  Layer 2: 公司知识库（Milvus/ChromaDB，RAG 检索）      │
│  Layer 3: 公司经验记忆（Milvus/ChromaDB，历史经验）     │
│                                                      │
│  执行后记录：                                          │
│  Agent 任务结果 → 自动提取关键决策 → 写入 Layer 3       │
└─────────────────────────────────────────────────────┘
```

**Layer 1 — 公司基础资料（静态注入）**

| 字段 | 说明 | 用途 |
|------|------|------|
| company_name | 公司名称 | Agent 回答中正确称呼公司 |
| industry | 行业分类 | 决定 Agent 回答的专业领域 |
| brand_description | 品牌描述 | 帮助 Agent 理解品牌定位 |
| target_audience | 目标受众 | 内容运营 Agent 的创作依据 |
| product_categories | 产品类目 | 选品搜索结果的相关性加权 |
| brand_voice | 品牌调性 | 决定内容生成的语气和风格 |
| competitors | 竞品列表 | 品牌商务 Agent 的竞品分析基准 |
| usp | 独特卖点 | 营销策略的核心参考 |
| social_media_accounts | 社媒账号 | 跨平台内容策略 |

**Layer 2 — 公司知识库（RAG 语义检索）**

**Hybrid 混合检索引擎**：BM25 关键词检索 + Milvus/ChromaDB 向量检索 + RRF 融合 + Cross-Encoder Reranker 精排。

**为什么用混合检索而非纯向量检索？**
- 纯向量检索在"达人合作规范""品牌调性"等概念性查询上表现好，但在"SKU-12345""合同编号 2024-088"等精确匹配上会漏
- BM25 关键词检索保证精确匹配不遗漏，向量检索保证语义相关不跑偏

**Layer 3 — 公司经验记忆（自动积累）**

Agent 每次完成任务后，自动提取关键决策和结果，写入经验记忆。下次 Agent 执行类似任务时，自动检索相关经验作为参考。

### 2A.4 Query Rewrite（查询改写）— P0 新增

**问题**：用户输入"帮我找美妆达人""这个数据对吗""上次那个方案改一下"，口语化表达直接送向量检索，召回效果差。

**方案**：在感知管道中新增 `QueryRewriter` 模块，在检索前执行。

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| MultiQuery | 生成多个查询变体，合并召回 | 通用，高召回率 |
| Decompose | 复杂问题拆解为子问题，分别检索 | 多跳推理问题 |
| HyDE | 先生成假设答案，再用假设答案检索 | 概念模糊的查询 |
| Self-Query | 提取 Metadata 过滤条件 | 需要按时间/类别过滤 |

**关键原则**：必须保留原始 query，改写 query 和原始 query 一起召回。改写出错时，原始 query 作为兜底。

### 2A.5 Chunk 策略优化 — P0 新增

**问题**：当前仅使用 `RecursiveCharacterTextSplitter(chunk_size=512)`，一刀切策略不能适应所有文档类型。

**方案**：自适应 Chunk 策略，按文档类型选择切分方式。

| 文档类型 | 切分策略 | 说明 |
|----------|----------|------|
| Markdown/技术文档 | 按标题层级切分 | 保留 # → ## → ### 层级 |
| PDF 报告/法律文档 | Page-Level 切分 | 页面边界 = 语义边界 |
| FAQ/短文档 | 固定 512 Token | 快速验证 |
| 政策/法规 | 按"条/款/项"结构 | 保留法律效力单元 |
| 表格密集文档 | 表格单独提取 | 不跨块切分 |
| 长篇教程/手册 | Parent-Child Chunk | 子 Chunk 300T 检索 + 父 Chunk 1200T 上下文 |

**Parent-Child Chunk**：检索时命中小 Chunk，返回对应父 Chunk，既保证召回精度又保留完整上下文。

### 2A.6 智能检索策略编排（AgenticRAG）

不同 Agent 角色关注的数据维度不同，AgenticRAG 根据 Agent 角色自动选择检索策略组合：

| Agent 角色 | 检索策略 | 原因 |
|-----------|----------|------|
| 品牌商务 | HYBRID + EXPERIENCE + GRAPH | 需要竞品关系(GRAPH) + 历史合作经验(EXPERIENCE) |
| 内容运营 | HYBRID + GRAPH | 需要理解内容类型与平台的关系 |
| 数据分析 | HYBRID + GRAPH + EXPERIENCE | 需要全维度数据 |
| 达人搜索 | HYBRID + EXPERIENCE | 需要历史搜索经验 |
| 仓储物流 | HYBRID | 场景单一 |
| 默认 | HYBRID + EXPERIENCE | 保守策略 |

**四种检索策略：**

| 策略 | 说明 | 代价 |
|------|------|------|
| HYBRID | BM25 + 向量 + RRF + Reranker | 中 |
| GRAPH | 知识图谱关系推理（NetworkX） | 高 |
| EXPERIENCE | 经验记忆检索（历史任务总结） | 低 |
| FULL | 三层上下文全部加载 | 极高 |

### 2A.7 上下文工程（Context Engineering）— P1 新增

检索结果不是直接拼接送入 Prompt，而是经过以下处理：

1. **去重**：相同内容去除，相邻 Chunk 合并
2. **压缩**：规则过滤 + LLM 摘要提取，围绕 query 过滤证据
3. **排序**：最相关放前面，同文档保持原始顺序，矛盾证据标注版本
4. **结构化**：跨文档按主题分组，时间序列按时间线排列
5. **证据质量判断**：置信度 ≥ 0.7 正常生成，0.4-0.7 标注"信息可能不完整"，< 0.4 拒答+追问

### 2A.8 生成约束（证据边界）— P1 新增

**RAG 生成 Prompt 必须明确的 4 条规则**：

1. 只基于给定上下文回答，不要使用训练数据中的知识
2. 上下文不足时明确说"无法判断"，不要编造
3. 每个关键结论尽量附来源标注 [来源X]
4. 不要把相似文档当作当前版本事实，注意版本号和时间戳

**拒答/追问机制**：证据不足、证据矛盾、权限不足时，系统应该拒答、追问或升级人工，而不是编造一个流畅答案。

### 2A.9 RAG 质量评估 — P1 新增

**建立最小评估集**（50-100 条高价值问题）：

| 问题类型 | 示例 | 数量 |
|----------|------|------|
| 高频用户问题 | "帮我找美妆达人" | 20 条 |
| 线上失败问题 | 历史错误回答 | 10 条 |
| 业务关键问题 | "这批达人 ROI 怎么样" | 15 条 |
| 多跳推理问题 | "竞品都在投哪些达人" | 10 条 |
| 精确匹配问题 | 错误码、SKU、版本号 | 10 条 |
| 越权/过期问题 | 跨公司数据、旧版本 | 10 条 |
| 应该拒答的问题 | 无证据的问题 | 10 条 |

**分阶段评估指标**：

| 阶段 | 指标 | 工具 |
|------|------|------|
| 检索 | Hit Rate@k, MRR, NDCG, MAP, Context Recall, Context Precision | RAGAS / 自研 |
| 生成 | Faithfulness, Answer Relevancy | RAGAS |
| 人工校准 | 抽样对比自动评估结果，校正偏差 | 人工 |

**版本追踪**：每次修改记录解析器版本、Chunk 策略版本、Embedding 版本、Prompt 版本、评估集版本，确保效果变化可归因。

### 2A.10 多模态检索

视觉设计 Agent 支持双路径：CLIP 向量化（自然图片） + MLLM 文本描述（截图/图表/仪表盘）。通过 Multi-Vector Retriever 实现摘要检索 + 原图生成。

### 2A.11 知识图谱（GraphRAG）

纯向量检索缺乏关系推理能力。知识图谱补全实体间的结构化关系。当用户问"我们的竞品都在投哪些达人"时，Agent 通过知识图谱推理出完整关系链。

### 2A.12 文档解析

支持 PDF、DOCX、HTML、TXT 格式入库。增强方案（P2）：
- PDF 多栏布局 → Layout-Aware Parser（LlamaParse/Docling）
- 扫描件 → OCR（Tesseract 4.x+，双引擎交叉校验）
- Word 标题层级 → python-docx 读取 Heading 样式，重建文档树
- 表格 → 单独提取 Markdown 化，不跨块切分
- 分层校验 → 格式校验 → 解析校验 → Chunking 校验，低质量数据不入库

### 2A.13 Prompt 构建与引用标注

检索到的参考资料通过标准 Prompt 模板注入 LLM，LLM 回答时标注 `[来源1]`、`[来源2]`，确保可追溯。

## 2B. 记忆系统

### 2B.1 为什么需要记忆系统

大语言模型每次对话都是"失忆"的——它不记得上一轮对话的内容，更不记得三天前的结论。记忆系统让 Agent 具备"记住"的能力。

**三层记忆，对应人类认知的三个层次：**

| 层次 | 类比 | 存储 | 容量 | 生命周期 |
|------|------|------|------|----------|
| 工作记忆 | 你正在想的事 | AgentState 运行时 | 极有限 | 单次任务 |
| 短期记忆 | 你今天做的事 | PostgreSQL + Redis | 最近 N 条 | 7 天 |
| 长期记忆 | 你学到的经验 | Milvus 向量库 | 可配置 | 永久 |

### 2B.2 工作记忆（Working Memory）

基于认知心理学 Baddeley & Hitch 工作记忆模型设计：

```
WorkingMemory {
  goal: "搜索美妆达人并评估合作价值"        // 当前任务目标
  current_step: "step_2"                   // 当前执行步骤
  context_focus: "search_kols"             // 注意力焦点
  temporary_variables: {                   // 中间结果
    step_results: [...],
    last_tool_output: "...",
    retry_count: 0
  }
  pending_actions: ["analyze_data","generate_outreach"]  // 待执行动作
}
```

**解决的问题**：Agent 在 Plan-Solve 模式下，需要记住当前执行到哪一步、哪些动作已完成、哪些待处理。工作记忆提供了单次任务周期的运行时状态管理。

### 2B.3 短期记忆（情景记忆）

存储最近 N 次任务的关键信息，使用 PostgreSQL + Redis 双写：

```
EpisodicMemory {
  agent_key: "达人搜索 Agent"              // 哪个 Agent 执行的
  task_summary: "搜索美妆达人，找到 5 位"    // 任务摘要
  key_decisions: ["选择抖音平台","按互动率排序"]  // 关键决策
  tools_used: ["search_kols","analyze_data"]    // 使用的工具
  outcome: "成功找到 5 位达人，已生成建联话术"   // 任务结果
  human_feedback: null                     // 用户反馈（可选）
  company_id: "1"                          // 多租户隔离
}
```

**解决的问题**：
- 用户问"刚才那个任务的结果是什么" → 从短期记忆中快速检索
- 用户反馈"不满意" → 记录反馈，供后续优化参考
- 积累到阈值（默认 50 条）→ 触发睡眠巩固

### 2B.4 长期记忆（语义记忆 + 睡眠巩固）

从短期记忆中提取模式，压缩为长期经验：

```
SemanticMemory {
  memory_id: "a1b2c3d4"                            // 唯一标识
  content: "美妆达人搜索：优先抖音平台，按互动率排序效果好"  // 记忆内容
  category: "达人搜索"                               // 分类
  embedding: [0.12, -0.34, ...]                    // 向量嵌入
  source_episodes: 5                                // 来源情景数（越多越可靠）
  confidence: 0.95                                  // 置信度（≥0.9 受 LRU 保护）
}
```

**睡眠巩固引擎**：

```
短期记忆积累 ≥ 50 条（或 30 分钟间隔）
  │
  ▼
1. 摘要压缩：提取关键模式
2. 去重：语义相似记忆合并，提升 source_episodes
3. 置信度更新：source_episodes 越多，置信度越高
4. 写入长期记忆（Milvus）
5. LRU 淘汰：最久未使用的低置信度记忆被淘汰
```

**解决的问题**：
- Agent 执行过 100 次达人搜索后，积累了"抖音美妆达人优先按互动率排序"的经验
- 下次执行类似任务时，自动检索这条经验，决策质量更高
- 避免了每次从零开始的"冷启动"问题

### 2B.5 程序性记忆（Procedural Memory）

更高层次的记忆，存储"怎么做"的元知识：

| 类型 | 说明 | 状态 |
|------|------|------|
| Few-shot 缓存 | 缓存最优的 Few-shot 示例 | 设计阶段 |
| Prompt 优化 | 根据历史效果自动优化 Prompt | 设计阶段 |
| LoRA 微调 | 对特定任务做轻量级微调 | 设计阶段 |

### 2B.6 记忆系统的实际效果

**场景：用户第一天使用 AgentX**

```
用户："帮我找美妆达人"
Master：搜索... 找到 5 位达人。没有历史经验参考，使用默认排序。
```

**场景：用户第 30 天使用 AgentX**

```
用户："帮我找美妆达人"
Master：正在检索历史经验...
  找到 5 条相关经验：
  - "优先抖音平台，互动率 > 3% 的达人合作效果好"（置信度 0.95，来源 12 次任务）
  - "粉丝量 10-50 万的达人建联回复率最高"（置信度 0.88，来源 8 次任务）
  - "美妆赛道达人报价均价 8000-15000/条"（置信度 0.92，来源 15 次任务）
  
  基于以上经验，为您搜索... 找到 5 位达人，已按历史最优策略排序。
```

注意：用户完全感知不到记忆系统的存在，但 Agent 的回答质量在持续提升。

## 2C. RAG 技术应用评估与优化建议（v3.3 新增）

> **评估依据**: JavaGuide RAG 系列文章（基础概念·文档处理·向量索引·知识库更新·GraphRAG·检索优化）
> **核心原则**: "RAG 优化不是'换一个更强 embedding 模型'这么简单，必须沿着完整链路拆分——数据决定上限，Chunk 决定召回粒度，评估决定能否持续优化"

### 2C.1 RAG 在当前项目中的适用场景分析

AgentX 面向电商达人 BD 的核心场景与 RAG 的匹配度评估：

| 场景 | RAG 依赖度 | 检索内容 | 必要性 |
|------|-----------|----------|--------|
| 达人搜索 | **高** | 达人数据库（粉丝量、互动率、品类标签） | 核心 RAG 场景 — 需从达人知识库中检索匹配 |
| 达人建联话术 | **中** | 品牌手册、历史话术模板、达人偏好 | RAG 辅助 — 检索品牌资料+历史经验增强话术质量 |
| 数据分析 | **中** | 达人数据、历史分析报告、行业基准 | RAG 辅助 — 检索历史数据供对比分析 |
| 内容脚本策划 | **中** | 品牌调性文档、历史脚本模板、平台规则 | RAG 辅助 — 检索品牌规范+历史优秀案例 |
| 物流跟踪 | **低** | 快递单号、物流状态 | 无需 RAG — 直接 API 查询，无需语义检索 |
| 竞品分析 | **中** | 公开竞品数据、行业报告 | RAG 辅助 — 检索公开数据，但竞品内部数据不可得 |
| 复盘报告 | **中** | 历史合作记录、ROI 数据 | RAG 辅助 — 检索历史任务数据汇总 |

**关键结论**：AgentX 的核心场景以**局部事实问答**为主（"找达人""查数据""分析报告"），而非多跳关系推理（"A 系统影响 B 服务再导致 C 故障"）。这与参考资料中"向量 RAG + Hybrid Search + Rerank 往往更划算"的场景高度吻合。

### 2C.2 各 RAG 组件贡献度评估

| 组件 | 当前优先级 | 对核心业务贡献 | 评估 |
|------|-----------|--------------|------|
| Hybrid Search（BM25+向量+RRF） | 已实现 | **高** — 达人搜索需要精确匹配品类名+语义理解 | 核心组件，必须保留 |
| Rerank（Cross-Encoder） | 已实现 | **高** — 粗召回精准度不够时，Rerank 是最后防线 | 核心组件，必须保留 |
| Query Rewrite（4种策略） | P0 | **高** — 用户口语化表达（"帮我找个靠谱的"）改写后召回率显著提升 | 核心组件，必须保留 |
| 自适应 Chunk 策略 | P0 | **中** — 达人数据库以结构化数据为主，非长文档 | 重要但非紧急，可 Phase 2 |
| Top-K 三段式分层管理 | P0 | **高** — 避免盲目扩大 Top-K 导致噪声和成本上升 | 核心组件，必须保留 |
| 上下文工程（去重/压缩/排序） | P1 | **中** — 当前场景上下文较短，去重/压缩收益有限 | Phase 2 验证后再引入 |
| 证据边界约束（拒答/追问） | P1 | **高** — 避免编造不存在的数据，对商务场景至关重要 | 核心组件，必须保留 |
| 最小评估集（50-100条） | P1 | **高** — 没有评估就无法判断优化是否有效 | 核心组件，必须保留 |
| **AgenticRAG（按角色切换策略）** | Should Have | **低** — 5 个 Agent 的检索需求差异不大，统一管线已足够 | ⚠️ **技术堆砌风险** |
| **GraphRAG（知识图谱）** | Should Have | **低** — 达人/竞品分析以局部事实为主，不涉及多跳关系推理 | ⚠️ **技术堆砌风险** |
| 多模态检索（图片/视频） | Could Have | **低** — 当前以文本数据为主，多模态内容占比低 | 可延后 |
| 三层记忆系统 | Must Have | **中** — 属于 Agent 记忆，非 RAG 核心，但经验积累有价值 | 保留但标注非 RAG 组件 |

### 2C.3 技术堆砌识别与降级建议

**什么是技术堆砌？** 参考资料明确指出：引入某项技术不是因为"它听起来高级"，而是因为"向量 RAG 的 badcase 已经明确指向了该技术要解决的问题"。

**识别出的技术堆砌项：**

#### 2C.3.1 GraphRAG（知识图谱）— 建议降级

**参考资料原文**："不要为了追新技术一上来就 GraphRAG。先用向量 RAG 做基线，把失败案例收集出来；只有当失败集中在关系、多跳、全局归纳这些问题上时，再引入图结构。"

**不适用原因**：
1. AgentX 核心场景是局部事实问答（"找达人""查数据""分析报告"），不涉及多跳关系推理
2. GraphRAG 构建成本极高：实体抽取、关系抽取、实体消歧、社区发现、摘要生成，每一步都需要 LLM 调用
3. 增量更新一篇文档可能牵动整片图，维护成本远超收益
4. 权限过滤在图上比在向量上复杂得多

**建议**: 从 Should Have 降级为 **Could Have**，仅在 badcase 明确指向"跨文档关系推理失败"时评估引入。

#### 2C.3.2 AgenticRAG（按角色切换检索策略）— 建议降级

**参考资料观点**："先做数据治理 → 建立最小评估集 → 调 Chunk 策略 → 引入 Hybrid Search → 加入 Query Rewrite → 加 Rerank → 做上下文压缩 → 完善生成约束"

**不适用原因**：
1. 5 个 Agent 的检索需求趋同：都是"在知识库中找相关内容"，差异不显著
2. 不同策略组合的收益尚未验证，增加系统复杂度
3. 统一 Hybrid Search + Rerank 管线已足够覆盖所有场景
4. 多策略切换增加调试和评估成本

**建议**: 从 Should Have 降级为 **Could Have**，先用统一管线验证效果，仅在特定 Agent 的 badcase 明确指向"检索策略不当"时再考虑。

### 2C.4 推荐的最适 RAG 方案

基于参考资料的生产调优优先级，结合 AgentX 实际场景，推荐以下分阶段方案：

#### Phase 1 — 核心 RAG 管线（MVP，必须落地）

按参考资料推荐优先级：

```
1. 数据治理（文档解析 + Metadata 标注 + 权限过滤）
2. 最小评估集（50 条真实业务问题，覆盖 7 种类型）
3. Hybrid Search（BM25 + 向量 + RRF 融合）
4. Query Rewrite（MultiQuery + Decompose，原始 query 保底）
5. Top-K 分层管理（recall 30-100 → rerank 5-10 → context 3-6）
6. Rerank（Cross-Encoder，粗召回扩大候选池后精筛）
7. 证据边界约束（Prompt 4 条规则 + 拒答/追问机制）
```

**这套管线足够覆盖 AgentX 所有核心场景，且复杂度可控。**

#### Phase 2 — 优化增强（验证后引入）

```
8. 自适应 Chunk 策略（按文档类型，带质量校验）
9. 上下文工程（去重 + 压缩 + 排序）
10. 版本追踪（每次改动记录参数版本，可回放对比）
```

#### Phase 3 — 按需引入（仅在 badcase 明确指向时）

```
11. AgenticRAG（仅当特定 Agent 检索失败率显著高于其他）
12. GraphRAG（仅当失败集中在多跳关系推理）
13. 多模态检索（仅当图片/视频类数据占比 > 20%）
```

### 2C.5 参考资料核心原则速查

| 原则 | 来源 | 对 AgentX 的指导 |
|------|------|-----------------|
| "先做数据治理，再谈检索优化" | RAG 检索优化 | 达人数据库的结构化质量比 embedding 模型更重要 |
| "Hybrid Search 是生产默认项，但别神化" | RAG 检索优化 | 达人搜索以结构化数据为主，Hybrid 增益有限但仍有必要 |
| "Top-K 不是越大越好" | RAG 检索优化 | 必须分层管理，避免噪声和成本 |
| "GraphRAG 不适合所有场景" | GraphRAG 详解 | AgentX 以局部事实问答为主，暂时不需要 GraphRAG |
| "不做评估，优化就是玄学" | RAG 检索优化 | 必须建立最小评估集，否则无法判断优化是否有效 |
| "RAG 不应该永远给答案" | RAG 检索优化 | 证据不足时拒答，比编造答案更可信 |
| "RAG 的瓶颈通常不在某一个参数" | RAG 检索优化 | 不要盲目换 embedding 模型，先排查整条链路 |

## 2D. LLM API 调用工程化（v3.4 新增）

> **参考资料**: 万字拆解 LLM 运行机制 + 大模型 API 调用工程实践
> **核心原则**: "大模型 API 调用，本质上是接入一个聪明但昂贵、偶尔排队、会被限流、输出还需要校验的外部系统"

### 2D.1 Token 预算管理

**参考资料核心观点**: "上下文窗口是极其稀缺的资源。即使模型宣称支持 1M 上下文，也不意味着可以毫无节制地堆砌数据。"

**Token 预算公式**:
```
window ≥ input_tokens + max_output_tokens
```
其中 input_tokens 至少包含：System Prompt + User Prompt + 历史消息 + RAG Context + 工具 Schema

**AgentX 的 Token 预算策略**:

| 场景 | 预估输入 | 预留输出 | 预算判断 |
|------|---------|---------|----------|
| 达人搜索 | 1,500-3,000T | 800T | 密钥空间充足，直接调用 |
| 数据分析 | 2,000-5,000T | 1,500T | 正常 |
| 脚本策划 | 3,000-6,000T | 2,000T | 需关注 RAG 片段数量 |
| 竞品分析 | 4,000-10,000T | 2,500T | 需压缩历史消息 |
| 复盘报告 | 5,000-12,000T | 3,000T | 最多保留最近 3 轮对话 |

**超预算降级顺序**（从 4.docx 生产架构）:
```
1. 删除低相关 RAG 片段
2. 压缩早期历史消息
3. 减少工具 Schema，只保留候选工具
4. 降低最大输出长度
5. 切换长上下文模型
6. 拒绝执行并提示用户缩小范围
```

### 2D.2 流式输出策略

**参考资料核心观点**: "Streaming 降低的是 TTFT，不是总成本。它改善用户体感，但取消、超时、断流、重连和半成品 JSON 解析全是新问题。"

**AgentX 流式输出配置**:

| 场景 | 交互模式 | 理由 |
|------|---------|------|
| 达人搜索 | 流式 | 结果列表逐步展示，用户感知"系统在工作" |
| 数据分析 | 流式 | 分析过程较长，需要进度感知 |
| 脚本策划 | 流式 | 脚本逐步生成，支持中途打断 |
| 物流跟踪 | 同步 | 查询结果短小，3 秒内完成 |
| 竞品分析 | 流式 | 分析报告较长 |
| 复盘报告 | 异步 | 数据汇总+报告生成耗时长 |

**SSE 协议注意事项**:
- 关闭 Nginx 代理缓冲 `proxy_buffering off`
- 处理换行符转义（模型输出中的 `\n` 会破坏 SSE 事件边界）
- 设置 `proxy_read_timeout 300s` 防止长生成被中间件切断

**流式异常处理四类场景**:
1. **用户取消**: 前端取消 → 后端取消供应商请求 + 解析流 + 后续任务 + 未提交缓存
2. **超时**: 分层记录（连接超时 / TTFT 超时 / 总时长超时）
3. **断流**: 记录 `finish_reason`，未正常结束标记 `INTERRUPTED`
4. **重连**: 服务端生成 `messageId` + 递增 `sequence`，缓存已发送片段

### 2D.3 重试与幂等策略

**参考资料核心观点**: "重试必须和幂等绑定。能重试的错误有限，不能让重试制造重复业务结果。"

**可重试错误**: 网络瞬断、连接重置、部分 5xx、504、供应商过载、429（需结合 Retry-After）
**不可重试错误**: 400 参数错误、401/403 鉴权错误、内容安全拒答

**指数退避公式**:
```
sleep = min(maxDelay, baseDelay * 2^retryCount) + random(0, jitter)
```
约束: 最大重试次数 2-3 次，总截止时间 15 秒

**幂等 Key 设计**:
```
tenantId:userId:conversationId:messageId:attemptGroup
```
- 同一 message 下的多次 attempt 只保留一个 final
- 避免用户狂点"重新发送"导致重复落库和扣费

### 2D.4 限流分层策略

**参考资料核心观点**: "限流不能只按 QPS。一个 500 Token 请求和一个 80K Token 请求对供应商的压力差两个量级。"

**限流维度**（按 4.docx 大模型网关详解）:

| 层级 | 限流策略 | 维度 |
|------|---------|------|
| 用户级 | 滑动窗口 + 日 Token 上限 | RPM、TPM、日预算 |
| 租户级 | 令牌桶 + 月度预算 | 同时请求数、月预算 |
| 模型级 | 令牌桶 + 并发信号量 | 模型并发数、Token 上限 |
| 供应商级 | 全局令牌桶 + 熔断器 | 供应商总配额 |

**核心原则**: "先扣预算，再发请求。扣不到就不要发给供应商，直接排队、降级或拒绝。"

### 2D.5 结构化输出策略

**参考资料核心观点**: "结构化返回的核心不只是'看起来像 JSON'，更关键的是让模型输出能被程序稳定消费。"

**AgentX 结构化输出场景**:

| 场景 | 结构格式 | 关键字段 |
|------|---------|----------|
| 达人搜索 | JSON Schema | `name`, `fans`, `engagement_rate`, `platform` |
| 数据分析 | JSON Schema | `quality_score`, `anomaly_flag`, `recommendation` |
| 脚本策划 | Markdown + 元数据 JSON | `segments`, `duration`, `products` |
| 物流跟踪 | JSON | `tracking_number`, `status`, `estimated_delivery` |

**失败兜底四级**（从 2.docx 大模型结构化输出详解）:
1. 本地校验（JSON Schema 校验字段和类型）
2. 轻量修复（只修复格式，不重新生成内容）
3. 降级 Schema（复杂对象拆成多个小对象）
4. 人工或规则兜底（高价值订单不依赖自动修复）

### 2D.6 结构化输出上线前检查清单（v3.5 增强）

**参考资料核心观点**: "结构化返回的核心不只是'看起来像 JSON'，更关键的是让模型输出能被程序稳定消费。"

**Schema 层**:
| 检查项 | 说明 |
|--------|------|
| 字段是否足够原子 | 不把多个语义揉进一个字段 |
| 枚举是否覆盖"信息不足""无需操作"等状态 | 负面状态和正面状态一样重要 |
| required 是否明确 | 明确哪些字段必填，不依赖模型"猜测" |
| additionalProperties 是否关闭 | 防止模型输出未定义字段 |
| 字段描述是否说明使用边界 | 不只是描述"是什么"，还要说明"怎么用" |
| 是否有 schemaVersion | 版本化管理，方便升级兼容 |

**模型调用层**:
| 检查项 | 说明 |
|--------|------|
| 是否使用供应商原生 Structured Outputs | 比 JSON Mode 更可靠 |
| 是否控制输出长度 | 避免 JSON 被截断 |
| 是否避免过高采样随机性 | 结构化输出任务不宜用高 temperature |
| 是否设计校验失败重试 Prompt | 告诉模型"哪里不符合 Schema，请修正" |

**服务端执行层**:
| 检查项 | 说明 |
|--------|------|
| 是否做 Schema 校验 | 供应商能力降低的是生成阶段出错概率，不替代边界防护 |
| 是否做业务校验和权限校验 | 参数合法不代表业务合法 |
| 写操作是否幂等 | 重试不产生重复业务结果 |
| 高风险操作是否二次确认 | 删除/修改/支付类操作 |
| 工具超时是否短路 | 避免无限等待 |
| 是否有审计日志和 traceId | 全链路可追溯 |

**降级层**:
| 检查项 | 说明 |
|--------|------|
| 解析失败是否进入人工队列或规则兜底 | 不让残缺数据进入业务库 |
| 工具失败是否禁止模型编造结果 | 没有事实依据时不继续编答案 |
| 是否统计失败率/错误类型/高频非法枚举 | 根据失败样本反推 Schema 和 Prompt 改进点 |

**五大常见误区**（从 2.docx）:
| 误区 | 正确做法 |
|------|----------|
| Temperature=0 就一定稳定 | 上下文过长/指令冲突/输出截断时仍会失败，必须 Schema 兜底 |
| 用了 Structured Outputs 就不用校验 | 供应商能力降概率，不替代边界防护，仍需防非法参数/越权/重放 |
| Schema 越复杂越好 | 从稳定字段开始，少用复杂组合关键字，核心字段先做好 |
| 工具越多 Agent 越强 | 工具越多选择空间越大，误调用概率上升，工具设计要小而清晰 |
| Function Calling 可以绕过业务权限 | 权限必须在服务端，Prompt 里的"不要越权"只是提醒，不是安全边界 |

## 2E. Agent 架构设计评估（v3.4 新增）

> **参考资料**: AI Agent 核心概念详解 + AI Agent 记忆系统详解
> **核心原则**: "大部分 Agent 项目跑起来不稳定，不是模型不够好。基础没搭好。"

### 2E.1 Agent vs Workflow 选型

**参考资料核心观点**: "执行路径能不能提前确定，是最简单的判断标准。能确定，用 Workflow。不能确定，用 Agent。"

**AgentX 各场景的选型判断**:

| 场景 | 执行路径 | 选型 | 理由 |
|------|---------|------|------|
| 达人搜索 | 可确定 | **Workflow** | 固定流程：意图识别 → 检索 → 排序 → 展示 |
| 数据分析 | 部分可确定 | **Agentic Workflow** | 全局 Workflow 管结构，子步骤 Agent 探索 |
| 脚本策划 | 不可确定 | **Agent** | 取决于品牌调性、达人人设、活动主题，需要动态决策 |
| 物流跟踪 | 可确定 | **Workflow** | 固定流程：查询 API → 格式化返回 |
| 竞品分析 | 不可确定 | **Agent** | 分析角度和深度取决于用户需求，无法预判 |
| 复盘报告 | 部分可确定 | **Agentic Workflow** | 数据汇总固定，分析建议动态 |

**参考资料选型法则**: "先用最简单的方式跑通，再根据实际失败模式决定升级哪一层。上来就搞 Multi-Agent、全靠模型动态推理、上下文不做任何管理，踩进去了再爬出来会很费劲。"

### 2E.2 Master Orchestrator 的 Agent Loop 设计

**参考资料核心观点**: "Agent Loop 每一轮大概做三件事：让 LLM 推理，调用工具，把工具结果写回上下文。"

**AgentX 的 Agent Loop**:
```
初始化: 加载 System Prompt + 可用工具列表 + 用户请求
  ↓
循环迭代:
  ├── 读取上下文 → LLM 推理下一步（调工具 or 直接回复）
  ├── 需要工具 → 生成 Function Calling 意图 → 业务侧校验 → 执行 → 结果回填
  └── 不需要工具 → 直接回复，退出循环
  ↓
安全兜底: 最大迭代 10 轮，Token 消耗阈值
```

**参考资料工程要点**:
- 最大迭代轮次 10-20 轮
- 上下文越长推理质量越差（"Lost in the Middle"）
- Context Engineering 是 Agent Loop 最关键的部分

### 2E.3 记忆系统优化

**参考资料核心记忆生命周期**:
```
编码(Encode) → 存储(Storage) → 提取(Retrieval) → 巩固(Consolidation) → 反思(Reflection) → 遗忘(Forgetting)
```

**记忆权重衰减公式**（从 3.docx 记忆系统详解）:
```
score = relevance × importance × decay(t)
其中 decay(t) = e^(-λt)
```

**当前 AgentX 记忆系统的优化建议**:

| 当前设计 | 参考资料建议 | 修正 |
|---------|-------------|------|
| 三层记忆（工作/短期/长期） | 短期记忆是 Session 级，长期记忆是跨 Session 的 | ✅ 方向正确，保留 |
| 睡眠巩固引擎 | 自我反思 + 精细化反思闭环 + 记忆聚类与合并 | 增强：增加 Reflect Loop（每个子任务结束触发验证） |
| 无遗忘机制 | 权重衰减 + 冲突解决 + 定期 Vacuum | **新增**：遗忘机制，避免向量库堆满过期噪音 |
| 无 Markdown 记忆 | Markdown 可作为轻量级记忆载体 | **新增**：项目级 CLAUDE.md 记录团队规范和工作流 |

**参考资料警示**: "很多团队舍不得删，结果检索召回里全是几年前的过期噪音，Agent 反而变得更不靠谱。"

**Markdown 记忆适用场景**（从 3.docx CLAUDE.md 机制）:
- 技术栈和版本信息
- 常用命令（构建、测试、lint）
- 架构决策和背后的理由
- 团队约定和项目特有的坑
- **不适合**: 大段日志、敏感密钥、高频变化的运行时数据

## 2F. 生产级系统架构（v3.4 新增）

> **参考资料**: AI 应用系统设计 + 大模型网关详解
> **核心原则**: "Prompt Demo 只证明'能回答'，生产级架构要证明'长期可控地回答'。"

### 2F.1 生产级架构分层

**参考资料推荐分层**（从 4.docx 系统设计）:

```
入口层 → 业务编排 → 模型网关 → Prompt/Context → RAG/Memory/Tool → 异步任务 → 评测观测
```

**AgentX 对应实现**:

| 层级 | 参考资料要求 | AgentX 实现 |
|------|-------------|-------------|
| 入口层 | 认证鉴权、请求标准化、限流防刷、幂等控制、PII 脱敏 | `ApiRequest` 含 requestId/tenantId/userId/sceneCode |
| 业务编排层 | 决定交互模式、上下文组装、工具权限 | Master Orchestrator + Agentic Workflows |
| 模型网关 | 多模型路由、fallback、限流熔断、Token 预算、成本归因 | `LLMGateway` 统一收口 |
| Prompt 管理 | 模板版本、变量注入、灰度发布、快速回滚、审计 | `PromptTemplate` + `PromptVersion` + `PromptRelease` |
| 上下文管理 | RAG/Memory/Tool 三类上下文分区注入 | `ContextAssembler` 分区域组装 |
| 评测观测 | Trace、评测集、回归测试、成本监控 | `EvaluationService` + `TraceService` |

### 2F.2 Prompt 版本管理

**参考资料核心观点**: "Prompt 在生产环境里应该被当成一种可版本化配置，不能散落成代码里的多行字符串。"

**AgentX 的 Prompt 管理模型**（5 个对象）:
```
prompt_template: 名称、场景、类型、状态
prompt_version: 具体内容、变量定义、模型参数、创建人、变更说明
prompt_release: 某版本发布到哪个环境、哪些租户、多少流量
prompt_run: 每次调用绑定的 Prompt 版本、变量摘要和 Token 用量
prompt_eval_result: 某 Prompt 版本在评测集上的结果
```

**核心规则**: "Prompt 变更要像代码变更一样可追踪，但发布频率可以比代码更高。"

### 2F.3 模型网关设计

**参考资料核心观点**: "模型网关是 AI 应用的模型调用控制面，负责路由、fallback、限流、熔断、Token 预算和成本归因。"

**参考资料判断是否需要 Gateway**:

| 条件 | AgentX 评估 |
|------|------------|
| 单应用、单模型、每天几百次 | ❌ 不适用 |
| 多业务线/团队调用模型 | ✅ 5 个 Agent 共享模型 |
| 多租户、配额管理 | ✅ 不同品牌客户 |
| 多供应商、需要 Fallback | ✅ 需要 |
| 合规审计、Prompt 版本管理 | ✅ 需要 |

**结论**: AgentX 需要 Gateway，但**第一版不需要完整实现**。最小可行 Gateway:
```
LLMGateway: 统一入口 + 日志 + usage + fallback
```

**参考资料的工程建议**: "你可以先不做完整 Gateway，但最好从第一天就把模型调用收在一个地方——一个统一的模块、一个统一的接口。"

### 2F.4 评测体系

**参考资料评测指标**（从 4.docx 系统设计）:

| 指标 | 含义 | AgentX 应用 |
|------|------|------------|
| Context Recall | 正确证据有没有被召回 | 达人知识库的召回率 |
| Context Precision | 放进上下文的片段有多少有用 | RAG 检索精准度 |
| Faithfulness | 答案是否忠于给定证据 | 达人数据是否准确引用 |
| Answer Relevancy | 答案是否回应了用户问题 | 是否回答了用户意图 |
| Tool Success Rate | 工具调用是否成功完成 | MCP 工具成功率 |
| Format Valid Rate | 结构化输出是否能被解析 | JSON Schema 校验通过率 |
| Cost per Success | 每次成功回答的平均成本 | 按租户和场景分摊 |

**评测闭环**（从 4.docx）:
```
线上失败样本 → 进入数据集 → 固定版本回放 → 定位 Prompt/RAG/Tool/模型问题 → 灰度新策略 → 对比指标 → 再发布
```

### 2F.5 参考资料核心原则速查

| 原则 | 来源 | 对 AgentX 的指导 |
|------|------|-----------------|
| "Token 预算不能只按字数估算" | LLM 运行机制 | 中文 1 Token ≈ 1.2-1.7 字，按 Token 算账 |
| "流式输出降低 TTFT，不降低总成本" | API 调用工程 | 达人搜索/分析用流式，物流/简单查询用同步 |
| "重试必须和幂等绑定" | API 调用工程 | 设计 `tenantId:userId:conversationId:messageId:attemptGroup` 幂等 Key |
| "先扣预算，再发请求" | 大模型网关 | 请求进网关先估算 Token 并扣限流桶 |
| "不要所有请求都用最强模型" | 大模型网关 | 意图分类/简单查询用小模型，复杂分析用强模型 |
| "Agent 和 Workflow 选型看执行路径能否确定" | AI Agent 核心 | 达人搜索用 Workflow，脚本策划用 Agent |
| "记忆不是越多越好，必须要有遗忘" | 记忆系统 | 权重衰减 + 冲突解决 + 定期清理 |
| "Prompt 要像代码一样做版本管理" | 系统设计 | 5 对象模型 + 灰度发布 + 快速回滚 |
| "没有评测就没有优化" | 系统设计 | 7 项指标 + 评测闭环 |
| "模型网关是稳定性入口" | 大模型网关 | 最小可行版：统一入口 + 日志 + usage + fallback |

## 2G. 上下文工程（Context Engineering）（v3.5 新增）

> **参考资料**: 上下文工程实战指南（3.docx）
> **核心原则**: "每次调用 LLM 之前，做一次 Context Assembler。上下文给对了，中等模型也能完成不少复杂任务。上下文给烂了，再贵的模型也会输出一堆看起来像答案的噪声。"

### 2G.1 Context Assembler 八步组装流程

**参考资料核心观点**: "工程里实际要做的事，说白了就是一句话：每次调用 LLM 之前，做一次 Context Assembler。"

**AgentX 的 Context Assembler 流程**:

```
输入: user_task, session_state, business_context

1. 加载系统约束（限制条件、策略规则、权限等）
   constraints = load_system_constraints()

2. 根据用户任务和会话状态，提取当前要达到的具体目标
   goal = extract_current_goal(user_task, session_state)

3. 使用 RAG 策略检索相关证据或上下文信息
   evidence = retrieve_rag(goal, business_context)

4. 回忆历史记忆或会话中已有信息
   memory = recall_memory(goal, session_state)

5. 根据目标、证据和记忆选择合适的工具/操作组件
   tools = select_tools(goal, evidence, memory)

6. 压缩会话历史消息，用于跨窗口上下文管理
   history = compact_history(session_state.messages)

7. 聚合所有上下文信息，并进行重要性排序
   context = rank([constraints, goal, evidence, memory, tools, history])

8. 根据模型的 Token 限额对上下文进行截断/裁剪
   context = fit_token_budget(context)

输出: messages, tool_schema, metadata
```

**两个关键步骤**:
- `rank` 决定哪些信息靠前哪些靠后
- `fit_token_budget` 决定哪些保留原文、哪些压成摘要、哪些只留一个引用

### 2G.2 静态规则：System Prompt 设计

**参考资料核心观点**: "System Prompt 应该是个持续调校的参数，不是写完就不动的配置文件。发现一个 failure case 就补一条规则，然后重新测试。"

**AgentX 的 System Prompt 设计原则**:

| 原则 | 说明 |
|------|------|
| 结构化 Markdown | 按角色、目标、约束、执行流、输出格式拆分，不揉成一大段 |
| Goldilocks zone | 具体到能引导行为、抽象到能覆盖常见变化，不过度设计也不过抽象 |
| 持续校准 | 先最小 Prompt 测基线，再根据 failure case 逐条补规则 |
| 固化到文件 | 规则固化到 `.cursorrules` 或 `CLAUDE.md`，方便团队维护 |

**两个极端要避免**:
1. **过度设计**: 把大量 if-else 逻辑硬塞进 Prompt，又长又脆弱
2. **过度抽象**: 只写一句"你要做一个有帮助的助手"，模型拿不到足够决策依据

### 2G.3 工具上下文：工具描述先讲边界

**参考资料核心观点**: "一个好的工具描述得能回答两个问题：什么时候该调用？什么时候不该调用？"

**AgentX 工具描述设计规范**:

| 规范 | 说明 |
|------|------|
| 一个工具只做一件事 | 避免"大而全"工具导致 Agent 犹豫，参数描述给格式示例 |
| 先讲边界 | 描述"什么时候不该调用"比"什么时候该调用"更能防止误调用 |
| 参数格式示例 | 参数描述中给出格式示例，降低误调用率 |

### 2G.4 动态上下文：RAG/记忆/工具结果不要一股脑塞

**参考资料核心观点**: "动态上下文真正容易翻车的地方通常不是'有没有检索'，而是检索错了、记忆过期了、工具超时了、摘要把证据丢了。"

**AgentX 动态上下文兜底策略**:

| 场景 | 兜底策略 |
|------|----------|
| 检索结果 | 先用评估集判断是召回/排序/生成哪个环节的问题，再决定优化方向 |
| 短期记忆 | 滑动窗口管理，过期结论通过 Compaction 压缩 |
| 长期记忆 | 权重衰减 + 冲突解决 + 定期清理 |
| 工具结果 | 先做裁剪和摘要，排障类信息保留原始引用（traceId/错误码/日志位置） |
| 工具结果清理 | 已消费的工具结果后续轮次清理，保留 tool_use 记录 |

### 2G.5 Few-shot 示例：别堆太多

**参考资料核心观点**: "典型错误是往 Prompt 里塞几十个 edge case 试图覆盖所有规则，结果模型过度拟合了示例表面的写法，反而忽略了真正该学的处理逻辑。"

**AgentX Few-shot 设计原则**:

| 原则 | 说明 |
|------|------|
| 3-5 个 canonical examples | 每个示例代表一类标准场景，不是把所有边缘情况列全 |
| 展示策略而非映射 | 示例展示的是"什么情况该用什么策略"，不是"这个输入必对应这个输出" |

### 2G.6 Token 预算：单次调用内怎么排优先级

**参考资料核心观点**: "这里管的是单次调用内的优先级，不是跨窗口的历史压缩。"

**优先级排序**（从高到低）:
```
1. 系统约束（角色、目标、安全规则）
2. 当前目标（用户这一轮要达成什么）
3. 证据（RAG 检索到的关键片段）
4. 记忆（相关历史经验）
5. 工具 Schema（本次可能用到的工具）
6. 历史消息（压缩后的摘要）
```

**裁剪策略**: 保留原文 → 压成摘要 → 只留引用 → 丢弃

### 2G.7 上下文工程工具生态

**参考资料对各工具的角色定位**:

| 工具类别 | 代表 | 角色 |
|----------|------|------|
| 编排框架 | LangChain / LangGraph | 管 Agent 的控制流、状态管理和循环调度 |
| 数据框架 | LlamaIndex | 偏 RAG，重点在数据摄取、索引构建和检索优化 |
| 向量数据库 | Chroma / Qdrant / Milvus / Pinecone | Embedding 存储和语义搜索 |
| 通信协议 | MCP | 工具标准化接入主程序 |
| Memory 产品 | Mem0 / LETTA / ZEP | Agent 记忆层，封装记忆写入/检索/遗忘生命周期 |

### 2G.8 上下文工程核心原则

| 原则 | 说明 |
|------|------|
| 高信噪比比信息量更重要 | 宁可上下文少一点但信噪比高，不因窗口大而多塞资料 |
| 长任务里上下文一定会变脏 | 早期判断/过期结论/已解决问题混进来，光靠"继续对话"撑不住 |
| 先做最简单的事 | 先把 System Prompt 和工具边界写清楚，再把 RAG 检索做准，再加摘要压缩和上下文预算，等长任务真遇到瓶颈再引入记忆层/Sub-agent |
| 每次改动都要版本化 | 给关键能力加版本锚点，别把某个模型或客户端的实现细节当成通用规律 |

## 5. 用户故事

### US-01: 与 Master 对话完成工作

> **As a** 电商商务人员  
> **I want** 打开一个对话窗口，用自然语言说出我想做的事  
> **So that** 我不需要学习任何操作，就像跟同事说话一样驱动 AI 完成工作

### US-02: 一句话触发达人搜索

> **As a** 电商商务人员  
> **I want** 说"帮我找美妆达人"就能看到达人列表  
> **So that** 我不需要知道搜索逻辑，结果直接出现在对话里

### US-03: 注册与登录

> **As a** 电商商务人员  
> **I want** 注册账号并安全登录  
> **So that** 我的对话记录和数据不会丢失

### US-04: 查看对话历史

> **As a** 电商商务人员  
> **I want** 在左侧看到历史对话列表  
> **So that** 我可以随时回顾之前的对话和结果

### US-05: 审核 Agent 产出

> **As a** 电商商务人员  
> **I want** 在对话中审核 Agent 产出的脚本和方案  
> **So that** 我可以确保最终交付的质量

## 6. 非功能性需求

| 类别 | 需求 |
|------|------|
| 性能 | SSE 流式响应，首字延迟 < 2s |
| 安全性 | JWT + bcrypt，输入过滤防 XSS |
| 上下文 | 子 Agent 返回结构化摘要，防止对话爆炸 |
| 可靠性 | 单个 Agent 失败不影响整体对话 |
| 可观测性 | 结构化日志，含 trace_id |

## 7. 设计原则

1. **对话即界面** — 所有功能通过对话触发，没有独立功能页面
2. **Agent 隐形** — 用户不知道也不关心背后有几个 Agent
3. **结果内联** — 产出物嵌入对话流，不跳转页面
4. **渐进发现** — 用户通过对话自然发现 Agent 能力
5. **先确认再执行** — 复杂任务先展示计划，等用户确认才执行
