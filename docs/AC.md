## US-11: RAG 技术应用合理性评估

> 基于 JavaGuide RAG 系列参考资料，确保 RAG 技术应用与业务需求高度匹配，避免盲目采用或过度复杂化

### AC-11.1 技术堆砌风险识别

| 编号 | 验收项 | 操作 | 预期结果 |
|------|--------|------|----------|
| AC-11.1.1 | 分阶段引入决策 | 检查 RAG 组件引入记录 | 每个新增组件附 badcase 分析报告，证明问题确实存在且该技术能解决 |
| AC-11.1.2 | AgenticRAG 引入决策 | 检查是否引入 AgenticRAG | 如已引入，存在特定 Agent 检索失败率 ≥ 2 倍平均值的 badcase 记录；如未引入，统一 Hybrid Search 管线覆盖所有场景 |
| AC-11.1.3 | GraphRAG 引入决策 | 检查是否引入 GraphRAG | 如已引入，存在明确的多跳关系推理失败 badcase（如"某系统影响了哪些服务"）；如未引入，核心场景以局部事实问答为主，无需图结构 |

### AC-11.2 过度工程化防范

| 编号 | 验收项 | 操作 | 预期结果 |
|------|--------|------|----------|
| AC-11.2.1 | 组件数量合理性 | 统计 Phase 1 已引入的 RAG 组件数 | 核心 RAG 管线 ≤ 7 个组件（数据治理、评估集、Hybrid Search、Query Rewrite、Top-K 分层、Rerank、证据边界） |
| AC-11.2.2 | 复杂度与收益匹配 | 审查每个新增组件的延迟/成本/维护负担 | 每个组件有明确的量化收益指标，不接受"感觉有提升"作为引入依据 |
| AC-11.2.3 | Phase 2/3 引入审查 | 任何 Phase 2/3 组件引入前 | 必须通过最小评估集验证，Context Recall 或 Faithfulness 有 ≥ 5% 的统计显著提升 |

## US-12: LLM API 调用工程化

> 基于万字拆解 LLM 运行机制 + 大模型 API 调用工程实践

### AC-12.1 Token 预算与流式输出

| 编号 | 验收项 | 操作 | 预期结果 |
|------|--------|------|----------|
| AC-12.1.1 | Token 预算估算 | 发送达人搜索请求（预估 3,000T 输入） | 网关层估算 `input_tokens`，预留 `max_output_tokens`，记录 `window ≥ input + output` 校验 |
| AC-12.1.2 | 超预算降级 | 发送超长上下文请求（超过窗口限制） | 按降级顺序：删除低相关片段 → 压缩历史 → 减少工具 Schema → 降低输出 → 切换模型 → 拒绝 |
| AC-12.1.3 | 流式输出 | 发送达人搜索请求 | 用户在 1 秒内看到首字（TTFT < 1s），内容逐步展示，Nginx 配置 `proxy_buffering off` |
| AC-12.1.4 | 流式取消 | 用户点击停止生成 | 后端取消供应商请求 + 解析流 + 后续任务，已生成内容标记 `INTERRUPTED`，不落成完整答案 |
| AC-12.1.5 | 流式断流处理 | 模拟网络中断 | 记录 `finish_reason`，未正常结束标记 `INTERRUPTED`，前端提示"已中断，可重新生成" |
| AC-12.1.6 | 同步/流式/异步选型 | 检查各场景交互模式 | 达人搜索/分析/策划/竞品分析走流式，物流跟踪走同步（3 秒内完成），复盘报告走异步 |

### AC-12.2 重试、幂等与限流

| 编号 | 验收项 | 操作 | 预期结果 |
|------|--------|------|----------|
| AC-12.2.1 | 可重试错误识别 | 模拟供应商返回 429/504 | 指数退避重试（2-3 次），总截止时间 15 秒，记录 `retry_count` 和 `route_reason` |

### AC-12.3 结构化输出上线前检查清单

> 基于大模型结构化输出详解（2.docx），上线前逐项检查

| 编号 | 验收项 | 操作 | 预期结果 |

| AC-12.3.2 | Schema 层 — 复杂度控制 | 检查 Schema 复杂度 | 从稳定字段开始，少用复杂组合关键字，核心字段/枚举/必填/额外字段限制先做好 |
| AC-12.3.3 | 模型调用层 — 供应商能力 | 检查是否使用供应商原生能力 | 使用供应商原生 Structured Outputs 或严格工具调用能力，控制输出长度避免 JSON 截断，避免过高采样随机性，设计校验失败重试 Prompt |
| AC-12.3.4 | 服务端执行层 — 校验 | 检查服务端执行 | Schema 校验 + 业务校验 + 权限校验，写操作幂等，高风险操作二次确认，工具超时短路，审计日志含 traceId |
| AC-12.3.5 | 降级层 — 兜底策略 | 模拟解析失败 | 解析失败进入人工队列或规则兜底，工具失败禁止模型编造结果，统计失败率/错误类型/高频非法枚举，根据失败样本反推 Schema 和 Prompt 改进点 |
| AC-12.3.6 | 常见误区规避 | 排查 5 大误区 | ① Temperature=0 不保证稳定（需 Schema 兜底）；② 用了 Structured Outputs 仍需服务端校验；③ Schema 不是越复杂越好；④ 工具不是越多 Agent 越强；⑤ 权限必须在服务端，不能藏在 Prompt 里 |
