# 用户画像聚焦决策 — 设计文档

> **日期**: 2026-06-18  
> **背景**: brainstorming 苏格拉底式讨论  
> **决策**: MVP 用户画像从"泛电商工作者"聚焦为"电商商务人员（达人 BD）"

---

## 1. 问题

原始 PRD 中用户画像覆盖过宽：电商运营专员、独立电商创业者、品牌市场负责人——三个不同角色，需求差异大，无法在一个 MVP 中同时满足。

## 2. 澄清过程

| 轮次 | 问题 | 回答 |
|------|------|------|
| 1 | "整个电商工作人员" vs "电商商务人员"你怎么划分？ | 按工作性质分：用电脑做机械性重复工作多的人 |
| 2 | 哪类人的机械工作最痛苦？ | 都觉得需要（运营/商品/达人/客服） |
| 3 | 你自己最熟悉哪个领域？ | 商务（达人 BD） |
| 4 | 商务场景最想让 AI 干的 3 件事？ | 智能筛选达人、自动生成建联话术、建联进度跟踪 + 竞品监控共 4 项 |
| 5 | 后续还想做其他方向吗？ | 想，但现在先聚焦商务 |

## 3. 决策

**MVP 用户画像聚焦为：电商品牌/商家的商务拓展人员（BD）**

核心场景：KOL/达人全流程管理 — 筛选 → 建联 → 跟踪 → 竞品监控

## 4. MVP 核心任务（按优先级排序）

| 优先级 | 任务 | 用户输入示例 |
|--------|------|-------------|
| P0 | 按条件智能筛选达人 | "帮我找美妆护肤+抖音+10万-50万粉丝的达人" |
| P1 | 自动生成个性化建联话术 | "给达人 @张三 写一封合作邀约，我们品牌是做美妆的" |
| P2 | 建联进度跟踪 | "我昨天联系了 5 个达人，现在哪些回复了？" |
| P3 | 竞品达人合作监控 | "最近有哪些美妆品牌在找抖音达人合作？" |

## 7. Master Orchestrator 架构决策（2026-06-18 第二轮 brainstorming）

### 7.1 问题

用户反馈：预想的是多 Agent 协作平台，由主 Agent 指导其他 Agent 工作，每个 Agent 配备 Skill 和 MCP 工具。之前的计划聚焦单 Agent（Amy）违背了设计初衷。

### 7.2 澄清过程

| 轮次 | 问题 | 回答 |
|------|------|------|
| 1 | 主 Agent 指导其他 Agent 的画面是什么？ | 用户对主 Agent 说"帮我做竞品分析"，主 Agent 自动拆任务、派给 Amy+Ben，汇总给我 |
| 2 | 第一期希望 Agent 协作完成什么场景？ | KOL 合作全生命周期：找达人→建联→试样物流→内容脚本→审核内容→跟踪数据→竞品分析→复盘 |
| 3 | Master vs AgentRuntime 区别？ | 不了解，需要解释 |
| 4 | 解释后选择？ | Master Orchestrator（CEO 模式），每个 Agent 干自己擅长的活 |
| 5 | 上下文窗口爆炸怎么办？ | 子 Agent 返回结构化摘要而非完整对话历史，WorkingMemory 存储摘要 |
| 6 | Reflect 用在什么地方？ | Master 用 Plan-Solve 拆任务 + Reflection 最终汇总审核；子 Agent 按任务类型选模式 |

### 7.3 决策：Master Orchestrator 架构

```
用户 → Master Orchestrator（Plan-Solve 拆任务 + Reflection 汇总审核）
                │
       a2a_delegate_task 派活
                │
    ┌───────────┼───────────┬──────────────┐
    ▼           ▼           ▼              ▼
  Amy        Ben          cc         warehouse
(ReAct)    (ReAct)    (Reflection)   (ReAct)
搜达人     分析数据    策划脚本      跟踪物流
写话术     竞品分析    内容审核
```

### 7.4 上下文窗口控制策略

| 策略 | 实现 |
|------|------|
| 子 Agent 只返回结构化摘要 | `a2a_delegate_task` 返回 `{agent, summary, key_data, tokens_used}` |
| WorkingMemory 存储摘要 | Master 的 `_build_initial_state` 中初始化 WorkingMemory |
| 每收一个结果 → 存摘要 → 释放上下文 | Master 不累积子 Agent 的完整对话 |
| 最终 Reflection 阶段汇总 | Master 用摘要做审核，不回溯原始对话 |

### 7.6 基础设施讨论结论

| 问题 | 结论 |
|------|------|
| 本地服务器撑不起大数据量？ | SQLite 单文件支持 140TB，MVP 数据仅数百 MB；计算走 DeepSeek API，不费本地资源 |
| 企业数据安全？ | 已有 JWT+bcrypt+输入过滤+prompt注入防护+公司级隔离+速率限制；需补 HTTPS 和 API Key 环境变量注入 |
| 传统 Web 合适吗？ | 合适。React+FastAPI 是标准方案。后续可选企业微信机器人作为入口 |
| 迁移到数据库后数据在哪？ | 数据库存的是文本索引（一条达人记录约1KB），不是原始视频/图片，你的电脑完全撑得住 |

### 7.7 不变的原则

- **不删代码**：所有 Agent 代码完整保留
- **多 Agent 从 MVP 开始**：Master + Amy + Ben + cc + warehouse 本期全部激活协作
- **用户即 PM**：开发者本人是商务领域专家，可自行判断功能是否正确
- **先协作链路跑通再优化**：两个 Agent 成功 a2a 协作后再加第三个
