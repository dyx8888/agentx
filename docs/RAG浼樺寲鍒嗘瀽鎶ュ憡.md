## 一、当前架构评估

### 1.1 现有能力矩阵

对照参考文档中的"生产级 RAG 9 步落地路径"，逐项评估当前状态：

| 步骤 | 参考文档推荐 | 当前实现 | 状态 |
|------|-------------|----------|------|
| 1. 数据治理 | 文档解析、去噪、标题层级、页码、表格、Metadata | `DocumentParser`（PDF/Word/HTML/TXT）+ `TextChunker`（RecursiveCharacterTextSplitter） | 部分实现 |
| 2. 最小评估集 | 50-100 条高价值问题，覆盖多类型 | `RAGEvaluator` 框架 + `rag_eval_dataset.json` | 部分实现 |
| 3. Chunk 策略 | 按场景对比固定/递归/语义/结构/Parent-Child | 仅 `RecursiveCharacterTextSplitter`，固定 512 Token | 需优化 |
| 4. Hybrid Search | BM25 + 向量 + RRF + Reranker | `HybridRetriever`：BM25 + 向量 + RRF + Reranker | 已实现 |
| 5. Query Rewrite | 改写、分解、HyDE、Self-Query | 无独立 Query Rewrite 模块 | 缺失 |
| 6. Rerank | Cross-Encoder 精排，分层 Top-K | `HybridRetriever` 内置 Reranker | 已实现 |
| 7. 上下文压缩 | 去重、裁剪、摘要、结构化抽取 | 无上下文压缩模块 | 缺失 |
| 8. 生成约束 | 证据边界、拒答、引用标注 | `rag_prompt.py` 有基础模板，缺失拒答逻辑 | 部分实现 |
| 9. 灰度与监控 | 版本记录、指标追踪、失败样本收集 | 无版本追踪机制 | 缺失 |

### 1.2 架构优势

- **HybridRetriever 四阶段流水线**（BM25 → 向量 → RRF → Reranker）与参考文档推荐完全一致，这已是业界标准
- **AgenticRAG 策略编排**：按 Agent 角色自动选择检索策略，避免了"一刀切"问题
- **DataInjector 三层注入**：Layer1 公司资料 + Layer2 知识库 + Layer3 经验记忆，设计合理
- **Embedding 缓存**：避免了重复计算，已对齐参考文档中"Embedding 缓存"建议
- **知识图谱 GraphRAG**：实体关系推理能力，补全了纯向量检索的不足

### 1.3 性能瓶颈

| 瓶颈 | 严重程度 | 影响 |
|------|----------|------|
| 无 Query Rewrite | 高 | 口语化查询（"这个咋整"）直接送检索，召回率低 |
| 单一 Chunk 策略 | 高 | 512 Token 固定切分可能切断关键事实，表格横跨 Chunk 边界 |
| 无上下文压缩 | 中 | 检索结果直接拼接，噪声文档占用 Token 且干扰模型注意力 |
| 无拒答机制 | 中 | 证据不足时强行生成，导致幻觉 |
| 无版本追踪 | 中 | 改参数后效果变好变差无法归因 |
| Top-K 单参数管理 | 中 | 只分粗召回 20 条和最终 5 条，缺少分层控制 |
| BM25 分词粗糙 | 低 | 仅空格分词，中文场景需上游预处理 |
| 无多模态处理 | 低 | 图片/表格内容被忽略 |

## 二、优化策略

### 2.1 Query Rewrite（查询改写）— 优先级 P0

**问题**：用户输入"帮我找美妆达人""这个数据对吗""上次那个方案改一下"，这些口语化表达直接送向量检索，召回效果差。

**方案**：新增 `QueryRewriter` 模块，位于感知管道（Perception Pipeline）中，在检索前执行。

```python
# app/rag/query_rewriter.py（新增）
class QueryRewriteStrategy(StrEnum):
    MULTI_QUERY = "multi_query"      # 生成多个变体，合并召回（LangChain MultiQueryRetriever）
    DECOMPOSE = "decompose"          # 复杂问题拆解为子问题，分别检索
    HYDE = "hyde"                    # 先生成假设答案，再用假设答案检索
    SELF_QUERY = "self_query"        # 提取 Metadata 过滤条件

class QueryRewriter:
    def rewrite(self, query: str, strategy: QueryRewriteStrategy, 
                conversation_history: list[dict] = None) -> list[str]:
        """
        输入："帮我找美妆达人"
        输出：["帮我找美妆达人", "搜索美妆品类 KOL 达人", "美妆护肤领域达人推荐"]
        
        关键原则（参考文档强调）：
        - 必须保留原始 query，改写 query 和原始 query 一起召回
        - 改写出错时，原始 query 作为兜底
        """
```

**验收标准**：
- 改写后的 query 保留原始意图，不引入新概念
- 原始 query 始终参与召回，改写 query 作为补充
- 改写延迟 < 200ms

### 2.2 Chunk 策略优化 — 优先级 P0

**问题**：当前仅使用 `RecursiveCharacterTextSplitter(chunk_size=512, chunk_overlap=50)`，一刀切策略不能适应所有文档类型。

**方案**：引入自适应 Chunk 策略，按文档类型选择切分方式。

```
文档类型判断 → 选择切分策略：

Markdown/技术文档 → 按标题层级切分（保留 # → ## → ### 层级）
PDF 报告/法律文档 → Page-Level 切分（页面边界 = 语义边界）
FAQ/短文档       → 固定 512 Token 切分（快速验证）
政策/法规        → 按"条/款/项"结构切分
表格密集文档     → 表格单独提取，不跨块切分
长篇教程/手册    → Parent-Child Chunk（子 Chunk 300 Token 检索 + 父 Chunk 1200 Token 上下文）
```

**Parent-Child Chunk 实现**（参考文档重点推荐）：

```
原始文档 → 切分成 300 Token 子 Chunk（用于向量检索）
         → 每个子 Chunk 挂载到 1200 Token 父段落（用于上下文注入）
         
检索时：命中小 Chunk → 返回对应父 Chunk → 保留完整上下文
```

**验收标准**：
- 支持按文档类型自动选择切分策略
- Parent-Child 模式下，检索精度和上下文完整性同时提升
- Chunk 质量校验：最小块 ≥ 50 Token，最大块 ≤ 5000 Token，标准差 ≤ 平均值的 50%

### 2.3 Top-K 分层管理 — 优先级 P0

**问题**：当前 Top-K 是一个参数管到底，从粗召回到最终上下文用同一个值。

**方案**：三段式 Top-K 管理（参考文档核心建议）。

```
recall_top_k: 30-100    → 粗召回候选池（BM25 + 向量，量要大以保证召回率）
rerank_top_n: 5-10      → Rerank 后保留（精排，量大但靠 Rerank 过滤）
context_top_n: 3-6      → 最终进入 LLM 上下文（极限压缩，只保留最有价值的证据）
```

**当前代码修改点**：[hybrid_retriever.py](file:///c:/kaifawenjian/agentdianshang/backend/app/rag/hybrid_retriever.py) 的 `search()` 方法应接受三个参数而非一个 `top_k`。

### 2.4 上下文工程（Context Engineering）— 优先级 P1

**问题**：检索结果直接拼接送入 Prompt，无压缩、无排序、无证据质量判断。

**方案**：新增 `ContextEngineer` 模块。

```
检索结果 → 

1. 去重：相同内容去除，相邻 Chunk 合并
2. 压缩（ContextualCompressionRetriever）：
   - 规则过滤：根据 Metadata 过滤低质量/过期文档
   - LLM 压缩：长片段围绕 query 做摘要提取
3. 排序：
   - 最相关证据放前面
   - 同文档相邻片段保持原始顺序
   - 矛盾证据标注版本和时间
   - 低置信度证据与高置信度证据分开
4. 结构化组织：
   - 跨文档对比 → 按主题分组
   - 时间序列分析 → 按时间线排列
   - 故障排查 → 按"现象→原因→处理步骤→注意事项"排列
```

### 2.5 Prompt 生成约束 — 优先级 P1

**问题**：当前 `rag_prompt.py` 缺少证据边界约束，模型在证据不足时仍会强行生成。

**方案**：完善 RAG 生成 Prompt，至少包含 4 条规则（参考文档强调）：

```
1. 只基于给定上下文回答，不要使用训练数据中的知识
2. 上下文不足时明确说"无法判断"，不要编造
3. 每个关键结论尽量附来源标注 [来源X]
4. 不要把相似文档当作当前版本事实，注意版本号和时间戳
```

**关键改进**：增加检索后证据质量判断，低置信度时触发拒答/追问/升级人工。

```
检索后判断：
├── 置信度 ≥ 0.7 → 正常生成，附引用
├── 置信度 0.4-0.7 → 生成 + 标注"信息可能不完整"
├── 置信度 < 0.4 → 拒答 + 追问用户澄清
└── 证据互相矛盾 → 列出矛盾 + 标注版本 + 请用户确认
```

### 2.6 评估体系 — 优先级 P1

**问题**：有 `RAGEvaluator` 框架，但缺少持续运行的评估闭环。

**方案**：

**A. 建立最小评估集（50-100 条）**

| 问题类型 | 示例 | 数量 |
|----------|------|------|
| 高频用户问题 | "帮我找美妆达人" | 20 条 |
| 线上失败问题 | 历史错误回答 | 10 条 |
| 业务关键问题 | "这批达人ROI怎么样" | 15 条 |
| 多跳推理问题 | "竞品都在投哪些达人" | 10 条 |
| 精确匹配问题 | 错误码、SKU、版本号 | 10 条 |
| 越权/过期问题 | 跨公司数据、旧版本 | 10 条 |
| 应该拒答的问题 | 无证据的问题 | 10 条 |

**B. 每条样本包含**

```json
{
  "question": "用户原始问题",
  "golden_answer": "理想答案",
  "golden_context": "应该命中的证据片段",
  "metadata_filter": "必要过滤条件",
  "answer_type": "事实问答/流程说明/对比/拒答/摘要"
}
```

**C. 检索和生成指标分开评估**

| 指标 | 衡量什么 | 工具 |
|------|----------|------|
| Context Recall | 正确证据是否进入候选池 | RAGAS |
| Context Precision | 候选池中正确证据的占比 | RAGAS |
| Faithfulness | 生成是否忠实于证据 | RAGAS |
| Answer Relevancy | 回答是否切题 | RAGAS |
| Hit Rate@k | Top-K 命中率 | 自研 |
| MRR | 第一个相关文档排名 | 自研 |

**D. 版本追踪**

每次修改记录以下版本（参考文档核心建议）：
- 文档解析器版本
- Chunk 策略版本
- Embedding 模型版本
- 索引参数版本
- Query Rewrite Prompt 版本
- Rerank 模型版本
- 生成 Prompt 版本
- 评估集版本

### 2.7 文档处理增强 — 优先级 P2

**问题**：当前 `DocumentParser` 不支持 Layout-Aware 解析、OCR、多版本解析对比。

**方案**：

| 增强项 | 方案 | 收益 |
|--------|------|------|
| PDF 多栏布局 | 引入 Layout-Aware Parser（LlamaParse/Docling） | 解决双栏 PDF 文本乱序 |
| 扫描件 OCR | 集成 Tesseract 4.x+，双引擎交叉校验 | 纸质文档可检索 |
| Word 标题层级 | `python-docx` 读取 Heading 样式，重建文档树 | 保留完整章节路径 |
| 表格处理 | 表格单独提取 → Markdown 化，不跨块切分 | 表格数据不丢失 |
| 多版本解析对比 | 同一 PDF 用两种解析器跑，不一致时标记人工审核 | 避免乱序文本入库 |
| 分层校验 | 格式校验 → 解析校验 → Chunking 校验 | 低质量数据不入库 |

### 2.8 多模态增强 — 优先级 P3

**问题**：当前仅支持 CLIP 向量化图片，但 CLIP 对截图、图表、仪表盘理解能力有限。

**方案**：引入 MLLM 描述 + 文本检索路径（参考文档推荐）。

```
图片处理双路径：
├── 路径 A（当前）：CLIP 向量化 → 向量检索 → 适用于自然图片
└── 路径 B（新增）：MLLM 生成文本描述 → 文本检索 → 适用于截图/图表/仪表盘

多向量检索（Multi-Vector Retriever）：
  图片 MLLM 摘要 → 文本向量索引（检索用）
  原始图片 → DocStore（生成用）
  检索命中摘要 → 拉取原始图片 → 交给多模态 LLM 生成
```

## 三、上下文工程与 RAG 的协同（v1.1 新增）

> **参考资料**: 上下文工程实战指南（3.docx）
> **核心原则**: "Context Engineering 做到最后，目的不是'Prompt 写得漂不漂亮'，而是每次调用 LLM 之前窗口里到底放了什么。改一个检索策略，换一种摘要方式，调整工具 Schema 的挂载顺序，有时候效果比换模型还明显。"

### 3.1 RAG 在 Context Assembler 中的位置

RAG 不是独立系统，而是 Context Assembler 八步流程中的第三步（证据检索）。RAG 优化必须放在整个上下文工程的框架下考量：

```
Context Assembler 八步:
1. 加载系统约束
2. 提取当前目标
3. RAG 检索证据 ← RAG 在这里
4. 回忆历史记忆
5. 选择合适工具
6. 压缩历史消息
7. 上下文排序
8. Token 预算适配
```

**关键洞察**: RAG 检索结果的质量不只看"检索到了什么"，还要看它进入上下文窗口后与其他信息（系统约束、记忆、工具结果、历史消息）的交互效果。检索回来的东西如果被排序靠后、被 Token 预算裁剪、与过期记忆冲突，那检索优化就白做了。

### 3.2 RAG 上下文与其他上下文的优先级竞争

在 Token 预算有限的情况下，RAG 证据需要与其他上下文竞争窗口空间：

| 优先级 | 上下文类型 | 说明 |
|--------|-----------|------|
| 1 | 系统约束 | 角色、目标、安全规则 — 不可裁剪 |
| 2 | 当前目标 | 用户这一轮要达成什么 — 保留原文 |
| 3 | **RAG 证据** | 检索到的关键片段 — 保留原文或压成摘要 |
| 4 | 记忆 | 相关历史经验 — 压缩后保留 |
| 5 | 工具 Schema | 本次可能用到的工具 — 必要时裁剪 |
| 6 | 历史消息 | 压缩后的摘要 — 优先丢弃 |

**对 RAG 优化的启示**:
- 不要盲目扩大 Top-K，检索回来的片段越多，被 Token 裁剪的概率越大
- 优先保证检索质量（信噪比）而非数量
- Context Recall 和 Context Precision 的平衡比单纯的高 Recall 更重要

### 3.3 上下文工程对 RAG 优化策略的补充

| RAG 优化策略 | 上下文工程视角的补充 |
|-------------|-------------------|
| Query Rewrite | 改写 query 不仅影响检索，还影响后续工具的 goal 提取和记忆召回 |
| Chunk 策略 | Chunk 大小影响 Token 预算裁剪时的粒度 — 大 Chunk 容易整体被裁 |
| Top-K 分层 | 三段式 Top-K 本质上是为 fit_token_budget 提供高质量的候选池 |
| 上下文去重/压缩 | 这是 Context Assembler 的 fit_token_budget 环节，不压缩则噪声挤占窗口 |
| 证据边界约束 | 拒答/追问机制是上下文工程的最后防线 — 证据不足时不编造 |

### 3.4 核心原则

| 原则 | 对 RAG 的指导 |
|------|-------------|
| "高信噪比比信息量更重要" | 宁少勿滥，检索精度优先于召回广度 |
| "长任务里上下文一定会变脏" | 过期检索结果要及时清理，避免旧证据干扰新判断 |
| "先做最简单的事" | 先把检索做准，再考虑复杂的上下文压缩和多策略编排 |
| "每次改动都要版本化" | 记录每次 RAG 参数变更时的上下文工程版本，方便归因 |

## 五、关键提醒

根据参考文档的经验教训，特别强调：

1. **不要只调 embedding**：RAG 的瓶颈通常在数据层面（解析质量、Chunk 策略），而不是 embedding 模型。先用评估集判断是召回问题、排序问题还是生成问题，再决定优化方向。

2. **不要跳过评估**：没有固定样本集，"感觉变好了"不是指标。RAG 的改动经常是局部变好、整体变差。

3. **不要盲目扩大 Top-K**：Top-K 变大会增加 Rerank 成本、Prompt Token、模型延迟，还会降低上下文信噪比。应该分层管理。

4. **不要把无关上下文塞给模型**：上下文窗口不是仓库。无关上下文会稀释注意力，给模型制造错误依据。

5. **不要忽略拒答能力**：RAG 不应该永远给答案。证据不足、证据矛盾、权限不足时，应该拒答、追问或升级人工。

6. **每次改动都要版本化**：记录解析器版本、Chunk 策略版本、Embedding 版本、Prompt 版本，否则效果变差时无法归因。

---

## 六、参考文档总结

> RAG 的瓶颈通常不在某一个参数，而在证据从原始文档走到最终答案的整条路径上。
> 
> 数据决定上限，Chunk 决定召回粒度，Hybrid Search 提升稳健性，Query Rewrite 解决表达差异，Rerank 决定证据顺序，上下文工程决定信噪比，评估决定能否持续优化。
