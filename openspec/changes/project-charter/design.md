## Context

AgentX 是一个面向中小型国内电商企业的 AI 数字员工协作平台。当前代码库已具备后端基础框架：FastAPI + LangGraph + MCP 工具链 + SQLAlchemy ORM + JWT 认证，以及 4 个电商职位 Agent（品牌商务、达人商务、内容创作、数据分析）。前端有一个 React（Ant Design）骨架但未对接后端。系统需要从"技术原型"升级为"可交付产品"。

**关键约束**：
- 目标用户是国内中小企业老板和电商从业者，非技术用户
- 数据敏感（平台凭证、LLM Key、经营数据），安全要求高
- 资源有限（小团队开发，需分阶段交付）
- 现有代码需尽量复用，避免推倒重来
- LLM API 费用由企业自付（企业提供自有 API Key），平台不承担调用费用

## Goals / Non-Goals

**Goals:**
- 定义清晰的产品边界和功能范围（减成本 + 增营收），作为所有后续开发的统一依据
- 建立 8 大电商职位的完整能力矩阵：品牌商务、内容运营、数据分析、客服专员、仓储物流、视觉设计、供应链选品师、智能投流专员
- 设计 Agent 间信息互通的核心机制：CompanyContextBus 共享上下文总线 + 异步任务链 + 实时通知
- 实现主流电商平台 API 的真实对接（抖音开放平台、淘宝开放平台、拼多多开放平台、蝉妈妈、生意参谋等），采用统一抽象 + 独立适配器架构
- 建立严格的多租户数据隔离规范（行级隔离 + 依赖注入）
- 实现企业级 RAG 知识库注入（三层数据架构：公司基础资料 → 公司知识库 → 公司经验记忆）
- 实现 AI 自动进化机制（四层记忆系统、程序记忆、记忆睡眠巩固三库联动、模型微调）
- 实现 Redis 消息队列的完整生产部署
- 直接使用 PostgreSQL 作为生产数据库
- 支持公司自定义 Agent（自定义 System Prompt + 工具集 + LLM 模型）
- 支持每个 Agent 独立配置大模型（根据任务复杂度分派不同模型）
- 企业老板驾驶舱支持 PWA 移动端适配
- 建立任务结果的三级人工审核机制（强制审核 / 推荐审核 / 自动通过）
- 支持 Agent 复用 MCP 协议工具，调用外部软件
- 建立 Harness 工程标准（类型检查、Lint、CI/CD、安全扫描、版本化 API）

**Non-Goals:**
- 不实现 IM 集成（企微/钉钉/飞书）——纳入远期规划
- 不替换现有技术栈（FastAPI/LangGraph/React/Ant Design），仅统一和扩展

## Decisions

### 1. 产品定位：面向国内电商的「虚拟团队即服务」——减成本 + 增营收

**决策**：AgentX = 可订阅的电商数字员工团队。企业注册 → 创建公司 → 订阅所需职位 → 数字员工自动开始工作。产品价值不仅在于降低人力成本，更在于通过 AI 选品、精准投流、数据洞察直接帮助企业增加营收。

**备选方案**：通用 AI Agent 平台（如 Coze、Dify）——放弃，因为通用平台缺乏电商垂直场景的职位分工和行业知识。

### 2. 执行引擎：统一为 AgentRuntime（Plan-Execute-Reflect）

**决策**：删除 `agent.py` 中手工构建的简易 StateGraph 和 `create_react_agent`，所有 Agent 统一走 `AgentRuntime` 引擎。每个 Agent 独立拥有完整的 Plan-Execute-Reflect 循环。

**理由**：当前存在三套执行路径（手工 StateGraph、create_react_agent、AgentRuntime），维护混乱。AgentRuntime 已经有了 Skill 注入、MemoryManager、DynamicValidator，是唯一完整的引擎。

### 3. Agent 间通信：统一为异步调度模式

**决策**：删除 `delegate_task`（同步 invoke 另一个 Agent 的 LLM），保留 `schedule_task` 作为唯一通信方式。Agent 向目标 Agent 提交 Task，目标 Agent 在自己的执行循环中消费。

**理由**：同步调用会导致单次 HTTP 请求串行调用多个 LLM，生产环境必超时。异步调度解耦 Agent 生命周期，职责清晰。

### 4. 共享上下文：CompanyContextBus 三层数据架构

**决策**：CompanyContextBus 承载公司级三层数据：

```
┌─────────────────────────────────────────────┐
│           CompanyContextBus                  │
├─────────────────────────────────────────────┤
│  Layer 1: 公司基础资料                        │
│  ├─ 品牌名/品类/经营平台/产品线                │
│  └─ 更新频率: 极少（企业注册时设定）            │
├─────────────────────────────────────────────┤
│  Layer 2: 公司知识库                          │
│  ├─ 产品信息/售后政策/品牌话术/SOP 流程         │
│  ├─ 更新频率: 低（企业手动维护或 Agent 建议更新）│
│  └─ 注入方式: RAG 检索增强生成                 │
├─────────────────────────────────────────────┤
│  Layer 3: 公司经验记忆                        │
│  ├─ Agent 工作产出摘要/决策记录/审核反馈        │
│  ├─ 更新频率: 高（每次任务完成后自动写入）       │
│  └─ 注入方式: 上下文窗口 + RAG 混合检索         │
└─────────────────────────────────────────────┘
```

Agent 完成任务后自动将摘要、关键数据写入 Layer 3。其他 Agent 可从总线读取对应层级的上下文。每层独立控制 company_id 隔离。

**理由**：目前 Agent 间只能点对点 delegate task，没有「我完成了一个事情，同事自动知道」的能力。三层架构确保不同粒度的信息各有合适的存储和检索方式，避免单一 RAG 库的信息噪音。

### 5. 前端技术栈：React + Ant Design Pro + PWA 移动端

**决策**：继续使用现有 React + Ant Design 技术栈。移动端采用 PWA（Progressive Web App）+ 响应式 Web 方案，不单独开发原生 App。

**理由**：Ant Design 有丰富的企业级组件，适合管理后台类应用。PWA 方案开发成本远低于原生 App（约 1/5），可满足老板在手机上查看 Dashboard、审批任务的核心需求，无需额外开发 iOS/Android。

### 6. 多租户隔离：强制行级隔离 + 依赖注入

**决策**：所有数据访问层操作必须附带 `company_id` 过滤。API 层通过 FastAPI 的 `Depends(get_current_active_user)` 自动注入 `company_id`，DAO 层所有查询方法第一个参数为 `company_id`。

**理由**：前序审计发现多处 `# TODO: Add proper permission checking`。必须从架构层面保证隔离，而非依赖开发者自觉。

### 7. LLM 策略：每 Agent 独立模型配置 + 企业自付 API Key

**决策**：不再采用统一的平台级 LLM 配置。改为：

- **企业提供自有 API Key**：平台不承担 LLM 调用费用，每家企业在 Company 表中配置自有 API Key（加密存储）
- **每 Agent 独立模型选择**：不同 Agent 根据任务复杂度选择不同模型

| Agent | 主模型 | 备选模型 | 选择理由 |
|-------|--------|---------|---------|
| 品牌商务 | DeepSeek-V3 | DeepSeek-R1（复杂策略） | 达人分析+话术生成，需要强文本能力 |
| 内容运营 | DeepSeek-V3 | DeepSeek-R1（创意策划）+ 多模态模型 | 脚本创作+多平台适配，Token 消耗最高 |
| 数据分析 | DeepSeek-V3 | MetricsEngine（零 LLM） | 核心指标用确定性计算，LLM 只做分析叙述 |
| 客服专员 | DeepSeek-V3 | 轻量模型（简单 FAQ） | RAG 增强，简单问题用轻量模型降成本 |
| 仓储物流 | DeepSeek-V3 | LogisticsEngine（零 LLM） | ERP 对接+物流跟踪走确定性引擎 |
| 视觉设计 | GPT-4V / 多模态模型 | DeepSeek-V3 | 多模态需求，图像理解和生成 |
| 供应链选品师 | DeepSeek-R1 | DeepSeek-V3 | 复杂市场分析和策略推理 |
| 智能投流专员 | DeepSeek-R1 | DeepSeek-V3 | 实时优化和策略调整 |

**理由**：按需分配模型，避免「一刀切」导致的成本浪费或能力不足。确定性引擎（MetricsEngine、LogisticsEngine）在关键路径零 LLM 依赖。

### 8. RAG 知识库：Hybrid RAG 完整生产管道

**决策**：采用业界 2025 生产标准的 Hybrid RAG 架构，而非简单 Naive RAG。检索管道四阶段流水线：

```
用户问题
    │
    ▼
┌─────────────────────────────────────────────┐
│ Step 1: 查询改写 (Query Rewriting)           │
│  ├─ HyDE: 生成假设文档用于检索                │
│  └─ 多查询变体: 生成 3 个语义变体扩展召回       │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ Step 2: 混合检索 (Hybrid Retrieval)          │
│  ├─ 向量检索 (Milvus): BGE-M3 Embedding     │
│  │   └─ 语义相似度 Top 20                    │
│  ├─ BM25 关键词 (PostgreSQL): pg_trgm +     │
│  │   tsvector 全文索引 Top 20               │
│  └─ RRF 合并去重 → 候选 25 条                 │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ Step 3: 重排序 (Reranking)                   │
│  ├─ BGE-Reranker-v2-m3 Cross-encoder 精排   │
│  ├─ 元数据过滤: company_id + partition       │
│  └─ 25 条 → 精排 → Top 5                     │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ Step 4: 注入 LLM 上下文                       │
│  └─ Top 5 文档 + 相关度评分 → 追加到         │
│     System Prompt                            │
└─────────────────────────────────────────────┘
```

**多模态检索**：视觉设计 Agent 使用 CLIP Embedding（512维）实现以图搜图，支持从历史素材库中检索风格参考。

**三层注入**：对应 CompanyContextBus 的三层数据架构，不同 Agent 按需注入不同层级数据。

**理由**：Naive RAG 召回率仅 75-80%，Hybrid RAG 可达 90-95%。RAG 是让 Agent 贴合每个企业实际情况的核心手段。客服需要产品信息 RAG，内容运营需要品牌话术 RAG，视觉设计需要多模态 RAG。Milvus 是国产向量数据库中最成熟的选择，原生支持混合检索。

### 9. 平台 API 对接：统一抽象 + 独立适配器

**决策**：采用统一 PlatformAdapter 抽象基类 + 每个平台独立 Adapter 实现的架构。

```
                 ┌──────────────────┐
                 │  PlatformAdapter │  ← 统一抽象基类
                 │  (abstract)      │
                 └────────┬─────────┘
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
┌─────────────────┐ ┌──────────┐ ┌─────────────────┐
│DouyinStarAdapter│ │Taobao    │ │Pinduoduo        │
│(抖音星图)        │ │Adapter   │ │Adapter          │
│                 │ │(淘宝开放)│ │(拼多多开放)      │
└─────────────────┘ └──────────┘ └─────────────────┘
          │               │               │
          ▼               ▼               ▼
┌─────────────────┐ ┌──────────┐ ┌─────────────────┐
│ChanmamaAdapter  │ │Shengyi   │ │  ...更多平台     │
│(蝉妈妈)          │ │Canshu    │ │                 │
│                 │ │(生意参谋) │ │                 │
└─────────────────┘ └──────────┘ └─────────────────┘
```

- 初期通过企业提供的 API Key 对接平台真实 API
- 测试初期可用 Mock 数据 + 浏览器操控（Playwright）从网页抓取作为降级方案
- 平台 Adapter 支持 company_id 参数，使用企业专属凭证

**平台接入优先级**：抖音开放平台（P0）→ 蝉妈妈（P0）→ 淘宝开放平台（P1）→ 生意参谋（P1）→ 拼多多开放平台（P2）→ 小红书（P2）

### 10. MCP 工具复用：自建核心 + 社区补充

**决策**：Agent 核心业务工具自建 MCP Server（如 search_kols、generate_outreach、inventory_check），通用工具从社区 MCP 生态复用（如浏览器操控、文件处理、代码执行）。

**安全边界**：MCP 工具分三级权限——只读工具（自动授权）、写入工具（需人工确认）、外部软件操控工具（需显式授权 + 操作日志审计）。

### 11. 任务审核：三级人工确认机制

**决策**：所有 Agent 的任务产出按风险等级分为三级审核：

| 级别 | 触发条件 | 处理方式 | 示例 |
|------|---------|---------|------|
| **强制审核** | 对外发送内容、涉及金钱/合同、平台操作 | 必须人工批准后才执行 | 达人邀约发送、广告投放、样品下单 |
| **推荐审核** | 重要但可逆的操作、策略建议 | 推送给用户，可一键通过或忽略 | 内容脚本、选品建议、设计稿 |
| **自动通过** | 低风险查询、内部数据处理 | 自动执行，仅在 Dashboard 展示 | 数据查询、库存检查、报告生成 |

**实现**：每个任务产出附带 `review_level` 字段，强制审核任务进入 `pending_review` 状态并推送 Dashboard 和企业主手机端（PWA 通知），超时未审核自动升级告警。

### 12. AI 自动进化：四层记忆 + 程序记忆 + 睡眠巩固 + 微调

**决策**：Agent 具备持续进化的能力，记忆系统从三层扩展为四层，新增程序记忆（Procedural Memory）——对标 LangMem 和 Mem0 2026 标准。

```
┌──────────────────────────────────────────────────────────────┐
│                     四层记忆系统                               │
├──────────────────────────────────────────────────────────────┤
│  工作记忆 (Working Memory)                                     │
│  ├─ 当前任务上下文、工具调用结果、中间产出                       │
│  ├─ 生命周期: 单次任务                                         │
│  └─ 存储: 进程内存 (LangGraph AgentState)                      │
├──────────────────────────────────────────────────────────────┤
│  短期/会话记忆 (Short-term / Session Memory)                    │
│  ├─ 近期任务摘要、用户偏好、审核反馈                             │
│  ├─ 生命周期: 数天到数周 (Redis TTL 7天 + PostgreSQL 兜底)      │
│  └─ 存储: Redis（热数据） + PostgreSQL（冷数据持久化）          │
├──────────────────────────────────────────────────────────────┤
│  长期语义记忆 (Long-term Semantic Memory)                       │
│  ├─ 经验模式、成功策略、失败教训（向量化）                       │
│  ├─ 生命周期: 持续积累                                         │
│  └─ 存储: Milvus 向量库 (BGE-M3 1024维 Embedding)             │
├──────────────────────────────────────────────────────────────┤
│  长期结构化记忆 (Long-term Structured Memory)                   │
│  ├─ 用户偏好 Profile、品牌调性、决策规则、累积模式               │
│  ├─ 生命周期: 永久                                             │
│  └─ 存储: PostgreSQL JSONB                                    │
├──────────────────────────────────────────────────────────────┤
│  程序记忆 (Procedural Memory)  ← 对标 LangMem/Mem0 2026        │
│  ├─ 优化 Agent 自身行为模式，而非存储数据                       │
│  ├─ 三个落地形态: Few-shot缓存 / Prompt规则自优化 / LoRA微调    │
│  └─ 存储: PostgreSQL + 文件系统                                │
└──────────────────────────────────────────────────────────────┘
```

**程序记忆三层落地（由浅入深）**：

| 级别 | 形态 | 说明 | 成本 | 实施阶段 |
|------|------|------|------|---------|
| Level 1 | Few-shot 缓存 | 存储成功交互对，相似场景自动注入为示例 | 极低 | 阶段六 |
| Level 2 | Prompt 规则自优化 | 分析审核反馈规律，自动生成 System Prompt 优化建议（需人工审核后生效） | 低 | 阶段六 |
| Level 3 | LoRA 微调 | 累积 ≥1000 条高质量数据后训练轻量适配器 | 中等 | 远期 |

**睡眠巩固 (Sleep Consolidation) — 三库联动**：
```
触发: 每日 03:00 或短期记忆 > 100 条
    │
    ▼
① PostgreSQL: 拉取未巩固短期记忆 (LIMIT 200)
    │
    ▼
② LLM 批量处理: 摘要压缩 (200→50条) + 去重合并 + 模式提取
    │ (~50K input + 6K output tokens)
    ▼
③ 分库写入:
  ├─ Milvus: 精华记忆向量化 → 写入长期语义记忆 (ltm_{company_id})
  ├─ PostgreSQL: 行为模式 → skill_evolution_log, 标记 consolidated=TRUE
  └─ Redis: 更新短期记忆缓存（精简版），清理已巩固条目
    │
    ▼
④ 失败重试: 连续 3 次失败 → audit_log → Dashboard 告警
```

**LoRA 微调 — 渐进式条件门控**：
```
前置条件 (缺一不可):
  ✅ 单个 Agent 累积 ≥ 1000 条高质量交互 (评分 ≥ 4/5)
  ✅ 企业主明确授权启动微调

训练架构:
  基座模型 (DeepSeek-V3/V3.1)  ← Frozen
    +
  LoRA Adapter (Rank 16-64, ~10-50MB)
    ├─ 方法: QLoRA (4-bit 量化, 1× RTX 4090 24GB → ~2-4h)
    └─ 推理部署: vLLM 多 LoRA 服务 (--lora-modules)

A/B 测试: 50% 流量 → LoRA版 / 原版 → 200 次交互 → LoRA领先 ≥5% → 推荐切换
```

**理由**：对标 Mem0 (LoCoMo 92.5分) 和 LangMem (语义+情景+程序三类型) 的 2026 标准。程序记忆是业界最重要的新方向——Agent 不只是记数据，而是优化自身行为。选择性记忆检索比全量上下文回放节省 70%+ Token，是成本刚需而非锦上添花。LoRA 微调为远期优化，前期用 Few-shot + Prompt 自优化覆盖 80% 收益。

### 13. 数据库：PostgreSQL — 结构化数据主存储 + 全文检索

**决策**：项目从一开始就使用 PostgreSQL，不再经过 SQLite 过渡期。

**PostgreSQL 精确角色边界**：

| ✅ 做 | ❌ 不做 |
|-------|--------|
| 业务主数据 (Source of Truth): companies/users/agents/tasks | 向量检索（虽可用 pgvector，但不替代 Milvus） |
| 审计日志 (Audit Log): 不可丢失的安全记录 | 高速缓存（由 Redis 负责） |
| 配置数据: company_agent_tools/skills/model_config | |
| 结构化长期记忆: feedback_log/decision_log/skill_evolution_log | |
| BM25 关键词检索: pg_trgm + tsvector（配合 Milvus 语义搜索） | |
| Token 消耗统计: token_usage_log/daily_usage_summary | |
| Row-Level Security (RLS): `WHERE company_id = current_setting('app.company_id')` | |

**理由**：SQLAlchemy ORM 已兼容 PostgreSQL。支持 JSON 字段、全文搜索、并发连接池，更适合多公司并发场景。与 Milvus（向量库）、Redis（缓存/队列）构成标准三层存储架构。SQLite 的并发写入锁在 Agent 协同场景下会成为瓶颈。

### 14. 基础设施：Redis 完整生产部署

**决策**：Redis 承担精确的生产角色，不做越界的事。

**Redis 精确角色边界**：

| ✅ 做 | ❌ 不做 |
|-------|--------|
| 会话状态: `session:{id}:state` TTL 24h | 长期数据存储（重启丢失 → 由 PG 兜底） |
| 任务队列: Redis Streams Consumer Group + ACK + 死信队列 | 向量检索（由 Milvus 负责） |
| 短期记忆热缓存: `memory:short:{company}:{agent}` TTL 7d | 大对象存储 (> 1MB → PG 或对象存储) |
| 实时状态推送: Pub/Sub `company:{id}:events` | |
| 限流计数器: `rate:{company}:{endpoint}` TTL 1min | |

**Redis Key 多租户隔离规范**：
```
c:{company_id}:agent:{agent_id}:session:{session_id}
c:{company_id}:queue:tasks
c:{company_id}:cache:short_term:{agent_name}
```

**理由**：Redis Streams 或 BullMQ 模式实现生产级任务调度，支持持久化、重试、死信队列。明确「做/不做」边界避免 Redis 被滥用为数据存储导致重启丢失。

### 15. 内容运营多平台上下文隔离

**决策**：内容运营 Agent 为每个经营平台（抖音/小红书/淘宝/拼多多）维护独立的上下文沙箱。通过 PlatformContextRouter 在任务执行时自动切换上下文，避免信息混杂和上下文爆炸。

```
┌─────────────────────────────────────────────┐
│         PlatformContextRouter               │
├─────────────────────────────────────────────┤
│  ┌──────────┐ ┌──────────┐ ┌──────────┐     │
│  │ 抖音沙箱  │ │小红书沙箱 │ │ 淘宝沙箱  │    │
│  │ - 账号   │ │ - 账号   │ │ - 账号   │     │
│  │ - 历史   │ │ - 历史   │ │ - 历史   │     │
│  │ - 策略   │ │ - 策略   │ │ - 策略   │     │
│  └──────────┘ └──────────┘ └──────────┘     │
└─────────────────────────────────────────────┘
```

### 16. 客服消息安全：三级发送策略

**决策**：客服 Agent 生成回复后，按置信度分级发送：

| 置信度 | 策略 | 说明 |
|--------|------|------|
| ≥0.95 | 静默发送 | 直接发送，事后可追溯 |
| 0.80-0.95 | 批量确认 | 汇总后一次性请企业主确认 |
| <0.80 | 逐条审核 | 每条必须人工确认后才发送 |

**实现**：通过 ModelGateway 的置信度评分 + 规则引擎综合判断。售后、投诉、补偿类消息强制走逐条审核。

### 17. 视觉设计：多阶段图像生成流水线

**决策**：视觉设计 Agent 采用分阶段生成流水线，而非端到端 AI 生成：

```
需求分析 → 风格参考检索（多模态 RAG）→ 主体生成 → 背景生成
→ 装饰元素 → 文字叠加（确定性渲染）→ 合规检测 → 多尺寸导出
```

**理由**：端到端 AI 生成在文字准确性和品牌一致性上不可靠。分离主体生成和文字叠加，确保文字由确定性渲染引擎处理。多模态 RAG（Milvus + CLIP）支持以图搜图找到历史参考素材。

### 18. 数据分析 MetricsEngine：确定性计算引擎

**决策**：数据分析 Agent 的核心指标计算使用确定性 MetricsEngine，零 LLM 依赖：

```
┌─────────────────────────────────────────────┐
│            MetricsEngine                     │
├─────────────────────────────────────────────┤
│  输入: 平台原始数据 (经 PlatformAdapter)      │
│  ┌───────────────────────────────────────┐  │
│  │  指标计算 (确定性)                     │  │
│  │  ├─ GMV / 客单价 / 转化率              │  │
│  │  ├─ ROI / CPA / CTR                   │  │
│  │  ├─ 同比 / 环比 / 趋势                 │  │
│  │  └─ 异常检测 (规则+统计算法)            │  │
│  └───────────────────────────────────────┘  │
│  ↓                                          │
│  结构化指标 JSON                             │
│  ↓                                          │
│  LLM 分析叙述层 (仅此层使用 LLM)              │
│  ├─ 指标解读                                │
│  ├─ 策略建议                                │
│  └─ 报告撰写                                │
```

**告警推送**：异常检测触发后，同时推送到老板 Dashboard（WebSocket）和相关 Agent（品牌商务/仓储物流）。

### 20. Harness 工程标准

**决策**：项目强制以下工程标准：
- **类型检查**：mypy / pyright 静态类型检查，pre-commit hook
- **Lint**：ruff (Python) + eslint (TypeScript)，CI 阻断
- **CI/CD**：GitHub Actions，PR 自动运行测试 + lint + typecheck
- **安全扫描**：bandit (Python) + npm audit (前端)，CI 阻断高危漏洞
- **版本化 API**：所有 API 路径包含 `/api/v1/` 前缀
- **测试覆盖率**：核心模块 ≥80%，集成测试覆盖关键路径

### 21. Milvus 精确角色：向量检索 + 多模态 RAG

**决策**：Milvus 承担精确的向量检索角色，不做越界的事。

**Milvus 精确角色边界**：

| ✅ 做 | ❌ 不做 |
|-------|--------|
| 知识库文档向量: `kb_{company_id}` / Partition 按类型隔离 | 结构化数据存储（由 PG 负责） |
| 长期经验向量: `ltm_{company_id}` / Partition 按 Agent 隔离 | 实时状态（由 Redis 负责） |
| 视觉素材向量: `visual_{company_id}` / CLIP Embedding 以图搜图 | 原始文件存储（用 MinIO/本地文件系统） |
| 多模态检索: 文本 BGE-M3 (1024维) + 图像 CLIP-ViT-B/32 (512维) | |

**多租户隔离**：每个企业独立 Collection (`kb_{company_id}`, `ltm_{company_id}`)，物理隔离，应用层强制注入 `company_id` 参数。

### 22. 三库多租户隔离策略

**决策**：PostgreSQL + Redis + Milvus 三库各自采用最合适的隔离方案：

| 层面 | PostgreSQL | Redis | Milvus |
|------|-----------|-------|--------|
| 隔离方式 | 行级 RLS | Key 前缀 | Collection 级 |
| 隔离粒度 | `WHERE company_id=N` | `c:N:*` | `kb_{id}`, `ltm_{id}` |
| 安全机制 | Row-Level Security + 应用层二次校验 | Key 命名规范 + 中间件强制注入 | RBAC + 应用层强制注入 |
| 泄露风险 | SQL 注入绕过 RLS → 应用层二次校验 | 错误 Key 前缀 → 中间件强制注入 | 错误 Collection → 应用层强制注入 |

**Redis Key 规范**：`c:{company_id}:{resource_type}:{resource_id}`

### 23. RAG 按职位分层注入策略

**决策**：不同 Agent 按需从 CompanyContextBus 三层数据中检索注入，不做「一刀切」的全量注入：

| 职位 | Layer 1 基础资料 | Layer 2 知识库 | Layer 3 经验记忆 | 特殊 RAG |
|------|:---------:|:---------:|:---------:|----------|
| 品牌商务 | ✅ | product + brand | 达人偏好/合作模式 | 达人画像检索（外部平台） |
| 内容运营 | ✅ | brand + product | 脚本模式/平台偏好 | 历史爆款内容检索（多平台隔离） |
| 数据分析 | ✅ | (极少) | 分析模式/指标偏好 | 外部平台 API（不经过 RAG） |
| 客服专员 | ✅ | product + sop | 回复模式/客户偏好 | 历史会话检索（最依赖 RAG） |
| 仓储物流 | ✅ | sop | (极少) | ERP/WMS 数据（不经过 RAG） |
| 视觉设计 | ✅ | brand + product | 设计模式/风格偏好 | 多模态 RAG（以图搜图） |
| 供应链选品师 | ✅ | product + market | 选品模式/季节模式 | 市场趋势检索（外部数据源） |
| 智能投流专员 | ✅ | product | 投放模式/ROI 偏好 | 平台投放数据（不经过 RAG） |

**理由**：不同 Agent 对 RAG 的依赖程度差异巨大。客服最依赖 RAG（几乎所有回复都需要知识库支撑），而仓储物流和数据分析主要通过确定性引擎工作，RAG 仅起辅助作用。按需注入避免不必要的检索开销和上下文污染。

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|---------|
| Agent 生成内容质量不稳定（LLM 幻觉） | Skill 机制注入专业知识限制输出范围；三级审核机制确保关键产出经过人工确认 |
| 多个 Agent 同时调用 LLM 导致 API 额度消耗过快 | 前端显示 Token 消耗；企业可设置每日额度上限；非实时任务用 Redis 队列削峰 |
| 小企业用户不懂如何配置 Agent | 每个职位提供预配置模板，用户开箱即用；高级配置折叠为可选项 |
| Agent 间上下文传递可能泄露跨公司数据 | CompanyContextBus 的 company_id 隔离与数据库同级强制检查 |
| 平台 API 对接稳定性（第三方接口变更/限流） | Adapter 模式隔离变更影响；Mock 降级方案；错误重试 + 指数退避 |
| RAG 知识库冷启动（新企业无数据） | 行业通用知识库兜底；引导企业上传基础资料；Agent 首次使用时主动询问关键信息 |
| Hybrid RAG 检索延迟增加（多阶段管道） | 查询改写缓存；BM25+向量并行检索；Reranker 仅对 <50 条候选排序 |
| 程序记忆 Few-shot 缓存积累到低质量案例 | 注入时按 success_rate 降序排列；定期清理低效缓存（success_rate < 0.5） |
| 三库运维复杂度（PG + Redis + Milvus） | Docker Compose 一键部署；提供运维文档和健康检查脚本；阶段零/一可选轻量模式 |
| LoRA 微调质量依赖高质量反馈数据 | 设置反馈数据最低阈值（N≥1000 条 + 评分≥4/5）；支持人工标注校正；A/B 测试验证后才能切换 |
| 睡眠巩固 LLM 调用成本 | 每日每 Agent ~50K tokens（约 ¥0.05-0.15/天/Agent）；按企业合计可控；失败不无限重试 |
| 多租户 RAG 检索跨公司数据泄露 | Milvus Collection 物理隔离 + 应用层二次校验 company_id；中间件层统一注入 |
