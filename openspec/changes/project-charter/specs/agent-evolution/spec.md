## ADDED Requirements

### Requirement: 四层记忆系统

每个 Agent MUST 维护四层记忆系统：工作记忆、短期/会话记忆、长期语义记忆、长期结构化记忆。四层记忆各有独立生命周期和存储策略。对标 LangMem 和 Mem0 (2026) 的企业级标准。

```
┌──────────────────────────────────────────────────────────────┐
│                     四层记忆系统                               │
├──────────────────────────────────────────────────────────────┤
│  工作记忆 (Working Memory)                                     │
│  ├─ 当前任务上下文、工具调用结果、中间产出                       │
│  ├─ 生命周期: 单次任务                                         │
│  └─ 存储: 进程内存 (LangGraph AgentState)                      │
├──────────────────────────────────────────────────────────────┤
│  短期/会话记忆 (Short-term / Session Memory)                    │
│  ├─ 近期任务摘要、用户偏好、审核反馈                             │
│  ├─ 生命周期: 数天到数周 (Redis TTL 7天 + PostgreSQL 持久化)    │
│  └─ 存储: Redis（热数据） + PostgreSQL（冷数据）                │
├──────────────────────────────────────────────────────────────┤
│  长期语义记忆 (Long-term Semantic Memory)                       │
│  ├─ 经验模式、成功策略、失败教训（向量化）                       │
│  ├─ 生命周期: 持续积累                                         │
│  └─ 存储: Milvus 向量库 (BGE-M3 Embedding, 1024维)            │
├──────────────────────────────────────────────────────────────┤
│  长期结构化记忆 (Long-term Structured Memory)                   │
│  ├─ 用户偏好 Profile、品牌调性、决策规则、累积行为模式           │
│  ├─ 生命周期: 永久                                             │
│  └─ 存储: PostgreSQL JSONB                                    │
└──────────────────────────────────────────────────────────────┘
```

#### Scenario: Agent 执行任务时自动加载多层记忆
- **WHEN** 品牌商务 Agent 开始新的达人筛选任务
- **THEN** 系统自动加载：工作记忆（当前任务上下文）+ 短期记忆缓存（近期达人偏好，从 Redis 读取）+ 长期语义记忆（历史成功合作模式，从 Milvus RAG 检索）+ 长期结构化记忆（品牌调性偏好，从 PG JSONB 读取）

#### Scenario: 任务完成后自动写入短期记忆
- **WHEN** Agent 完成一个任务（无论成功或失败）
- **THEN** 系统自动将任务摘要、关键决策、用户反馈写入短期记忆存储（Redis 缓存层 TTL 7天 + PostgreSQL 持久化兜底）

#### Scenario: 长期结构化记忆独立写入
- **WHEN** 企业主多次修改同一类型决策（如连续 5 次改动了客服回复的语气风格）
- **THEN** 系统在 skill_evolution_log 中累积该偏好模式，当累积 ≥5 次时固化为长期结构化记忆（PG JSONB），后续所有同类任务自动注入该约束

### Requirement: 程序记忆（Procedural Memory）

系统 MUST 支持程序记忆——优化 Agent 自身行为模式，而非存储数据。对标 LangMem 2026 标准，程序记忆有三层落地形态，由浅入深递进实施。

```
程序记忆三层落地（由浅入深）:

  Level 1: Few-shot 缓存（阶段六实施，成本极低）
  ┌─────────────────────────────────────────┐
  │ 存储成功交互案例（输入→输出对），当遇到  │
  │ 相似场景时自动从 Milvus 检索并注入为      │
  │ few-shot example                        │
  │                                         │
  │ 例：客服 Agent 遇到"退货咨询"时，自动    │
  │ 检索最近5次成功的退货处理对话作参考        │
  │                                         │
  │ 存储: PostgreSQL few_shot_cache 表       │
  │ + Milvus input_embedding 向量            │
  │ 注入条件: 向量相似度 > 0.85 +            │
  │   success_rate 降序 Top 5               │
  └─────────────────────────────────────────┘

  Level 2: Prompt 规则自优化（阶段六实施，成本低）
  ┌─────────────────────────────────────────┐
  │ Agent 分析审核反馈规律，自动生成          │
  │ System Prompt 优化建议，经人工审核后生效  │
  │                                         │
  │ 流程:                                    │
  │ ① 收集过去 50 次审核中的"修改"和"拒绝"   │
  │ ② LLM 分析修改模式                       │
  │    (如: 5次修改都在"增加互动引导")       │
  │ ③ 生成 System Prompt 优化建议            │
  │ ④ 推送企业主审核                          │
  │ ⑤ 通过后更新 Agent System Prompt          │
  │ ⑥ 记录 skill_evolution_log              │
  │                                         │
  │ 成本: 仅 LLM 分析 + 人工审核              │
  │ 间隔: 每累积 50 条审核决策触发一次         │
  └─────────────────────────────────────────┘

  Level 3: LoRA 微调（远期，需满足前置条件）
  ┌─────────────────────────────────────────┐
  │ 累积足够高质量数据后，训练轻量适配器，     │
  │ 让模型真正「内化」领域模式                │
  │                                         │
  │ 前置条件（缺一不可）:                     │
  │ ✅ 单个 Agent 累积 ≥ 1000 条交互          │
  │ ✅ 交互评分 ≥ 4/5                        │
  │ ✅ 企业主明确授权                         │
  └─────────────────────────────────────────┘
```

#### Scenario: Few-shot 缓存自动注入
- **WHEN** 客服 Agent 收到一条关于「退换货流程」的用户咨询
- **THEN** 系统从 few_shot_cache 中检索相似度高且成功率高的历史交互，将 Top 3 作为 few-shot example 自动注入到 Agent 的 System Prompt 中

#### Scenario: Few-shot 缓存质量降级
- **WHEN** 某条 few-shot 缓存的 success_rate 连续低于 0.5
- **THEN** 系统自动标记为降级，不再注入，30 天后自动清理

#### Scenario: Prompt 规则自优化触发
- **WHEN** 品牌商务 Agent 累积了 50 条审核反馈（包含修改和拒绝）
- **THEN** 系统自动触发 Prompt 分析：识别高频修改模式 → 生成优化建议 → 推送 Dashboard 审核

#### Scenario: 企业主拒绝 Prompt 优化建议
- **WHEN** 企业主审核后拒绝了某条 Prompt 优化建议
- **THEN** 系统记录拒绝原因 → 该模式在未来 30 天内不再重复生成同类建议 → 记录 EvolutionLog

### Requirement: 记忆睡眠巩固（三库联动）

系统 MUST 支持在低峰时段对 Agent 短期记忆进行「睡眠巩固」：摘要压缩、去重、模式提取，将高价值经验迁移到长期语义记忆。整个过程涉及 PostgreSQL → LLM → Milvus → Redis 三库联动。

```
睡眠巩固三库联动流程:

  触发: 每日 03:00 UTC 或短期记忆 > 100 条
      │
      ▼
  ① PostgreSQL 拉取
  ┌─────────────────────────────────────────┐
  │ SELECT * FROM agent_short_term_memory    │
  │ WHERE company_id=? AND agent_name=?      │
  │   AND consolidated = FALSE               │
  │ ORDER BY importance DESC                 │
  │ LIMIT 200                                │
  └─────────────────────────────────────────┘
      │
      ▼
  ② LLM 批量处理
  ┌─────────────────────────────────────────┐
  │ 输入: 200 条短期记忆 (每条 ~200 tokens)   │
  │ Prompt: 摘要压缩 + 去重合并 + 模式提取    │
  │ 输出: ~50 条精华记忆 + 5 条行为模式       │
  │ 成本: ~50K input + ~6K output tokens     │
  └─────────────────────────────────────────┘
      │
      ▼
  ③ 分库写入
  ┌─────────────────────────────────────────┐
  │ ├─ Milvus: 精华记忆 → 向量化 (BGE-M3)    │
  │ │   → 写入 ltm_{company_id} 长期语义记忆  │
  │ ├─ PostgreSQL: 行为模式                  │
  │ │   → skill_evolution_log               │
  │ │   标记原记录 consolidated=TRUE         │
  │ └─ Redis: 更新短期记忆缓存（精简版）       │
  │     清理已巩固的缓存条目                   │
  └─────────────────────────────────────────┘
      │
      ▼
  ④ 失败重试: 连续 3 次失败 → audit_log → Dashboard 告警
```

**触发条件**：
- 定时触发：每日凌晨 03:00 UTC 自动执行
- 阈值触发：某 Agent 未巩固短期记忆超过 100 条时自动触发该 Agent 的睡眠巩固

#### Scenario: 每日睡眠巩固自动执行
- **WHEN** 每日凌晨 3:00 触发睡眠巩固任务
- **THEN** 系统按 Agent 依次执行：PG拉取→LLM压缩→Milvus写入长期语义记忆→PG写入行为模式→Redis更新缓存→标记 consolidated=TRUE→记录 EvolutionLog

#### Scenario: 阈值触发睡眠巩固
- **WHEN** 某 Agent 的未巩固短期记忆超过 100 条
- **THEN** 系统自动触发该 Agent 的睡眠巩固，无需等待定时

#### Scenario: 巩固失败重试
- **WHEN** 睡眠巩固过程中 LLM 调用失败
- **THEN** 系统记录错误→1小时后自动重试→连续失败 3 次后推送告警到 Dashboard

#### Scenario: 巩固后 Redis 缓存同步
- **WHEN** 睡眠巩固完成，长期记忆已写入 Milvus
- **THEN** 系统同步更新 Redis 中的短期记忆缓存：删除已巩固条目，保留精简版摘要（每条 ≤ 80 tokens），确保后续 Agent 读取时获得最新状态

### Requirement: Agent 进化日志（EvolutionLog）

系统 MUST 记录每个 Agent 的进化过程：配置变更、记忆巩固、Skill 更新、模型微调等。EvolutionLog 用于追溯 Agent 的行为变化和性能趋势。

#### Scenario: 企业主查看 Agent 进化历史
- **WHEN** 企业主在 Agent 状态面板点击「进化日志」
- **THEN** 系统按时间线展示该 Agent 的所有进化事件：配置变更、记忆巩固、模型切换、Skill 更新

#### Scenario: 平台管理员审计 Agent 进化
- **WHEN** 平台管理员需要审计某公司的 Agent 行为变化
- **THEN** 系统按时间范围和 Agent 过滤 EvolutionLog

### Requirement: 模型微调（LoRA Fine-tuning）——渐进式三阶段

当某个 Agent 积累了足够的高质量反馈数据时，系统 SHALL 支持 LoRA 微调流程。微调为可选功能，企业自主决定是否启用。LoRA 微调属于程序记忆 Level 3，为远期优化——前期用 Few-shot 缓存 + Prompt 自优化覆盖 80% 收益。

**渐进式三阶段路径**：

```
═══════════════════════════════════════════════════════════════════════
阶段一：Few-shot 缓存（阶段六实施，成本极低）
═══════════════════════════════════════════════════════════════════════
  ┌─────────────────────────────────────────┐
  │ 原理: 存储高质量交互对 (输入→输出)        │
  │ 遇到相似场景 → Milvus 检索相似案例       │
  │ → 注入为 few-shot examples              │
  │                                         │
  │ 存储:                                    │
  │ ├─ PostgreSQL: few_shot_cache 表         │
  │ │   ├─ input_summary (问题描述)          │
  │ │   ├─ output_summary (成功输出)         │
  │ │   ├─ usage_count (被引用次数)          │
  │ │   └─ success_rate (成功率 0-1)        │
  │ └─ Milvus: input_embedding (BGE-M3)     │
  │                                         │
  │ 效果: 中等 (不改变模型行为，仅提供参考)    │
  │ 实施周期: 2-3天                          │
  └─────────────────────────────────────────┘

═══════════════════════════════════════════════════════════════════════
阶段二：Prompt 规则自优化（阶段六实施，成本低）
═══════════════════════════════════════════════════════════════════════
  ┌─────────────────────────────────────────┐
  │ 原理: Agent 分析审核反馈规律，自动生成     │
  │ System Prompt 优化建议                   │
  │                                         │
  │ 流程: 见「程序记忆」Level 2               │
  │                                         │
  │ 效果: 高 (直接从用户反馈中学习)            │
  │ 实施周期: 1周                            │
  └─────────────────────────────────────────┘

═══════════════════════════════════════════════════════════════════════
阶段三：LoRA 权重微调（远期，需满足前置条件）
═══════════════════════════════════════════════════════════════════════
```

**LoRA 微调前置条件（缺一不可）**：
- ✅ 单个 Agent 累积 ≥ 1000 条高质量交互（评分 ≥ 4/5）
- ✅ 企业主明确授权启动微调

**训练架构**：
```
基座模型 (DeepSeek-V3/V3.1)
   ├─ Frozen (不更新权重)
   └─ LoRA Adapter (训练)
        ├─ Rank: 16-64
        ├─ 参数量: ~10-50MB
        ├─ 目标层: q_proj + v_proj + o_proj
        └─ 方法: QLoRA (4-bit 量化)
```

**训练配置**：
- GPU: 1× RTX 4090 24GB (7B 模型) 或 1× A100 40GB (70B 模型)
- 时间: ~2-4 小时 / 企业
- 输出: ~50MB .safetensors 文件
- 框架: HuggingFace PEFT + bitsandbytes

**推理部署（多租户 LoRA 服务）**：
```
共享基座模型 (DeepSeek-V3)
  ├─ Company A LoRA (客服)  ~50MB
  ├─ Company B LoRA (客服)  ~50MB
  ├─ Company C LoRA (品牌商务) ~50MB
  └─ ...

vLLM 多 LoRA 服务:
  --lora-modules company_a=/models/lora/company_a/
  请求时指定: {"model": "deepseek-v3", "lora": "company_a"}
```

**成本分析（单企业单 Agent）**：
- 训练 GPU: ~¥15-35 (云GPU按需)
- 存储: ~50MB 永久
- 推理额外延迟: ~5-10% (合并权重后降为 0)
- 每 1000 token 推理额外成本: ~¥0.001

**A/B 测试流程**：
1. 随机分配 50% 流量到 LoRA 版
2. 收集 200 次交互的评分数据
3. 对比：LoRA版评分 vs 原版评分
4. LoRA版领先 ≥ 5% → 推荐切换
5. 否则 → 保留原版，微调数据存档用于后续分析

#### Scenario: 触发微调条件检查
- **WHEN** 客服 Agent 累计了 1000 条评分 ≥ 4/5 的交互记录
- **THEN** 系统推送通知到 Dashboard：「客服专员已有足够数据，建议进行模型微调以提升服务质量」→ 企业主可选择执行或延后

#### Scenario: 微调执行
- **WHEN** 企业主确认执行微调
- **THEN** 系统启动异步微调任务→Dashboard 显示进度→完成后进行 A/B 对比测试→测试报告推送审核→企业主批准后切换

#### Scenario: 微调质量不达标
- **WHEN** A/B 对比测试显示微调版效果不如原版（评分差距 < 5%）
- **THEN** 系统输出对比报告→建议不切换→保留原版→微调数据存档用于后续分析→记录 EvolutionLog 标记失败原因

#### Scenario: 多 LoRA 并发推理
- **WHEN** 多个企业同时使用各自微调后的 Agent
- **THEN** vLLM 服务根据请求中的 `lora` 参数自动切换对应的 LoRA 适配器，共享基座模型权重，每个 Adapter 额外开销仅 ~50MB GPU 内存

### Requirement: Skill 自动优化建议

系统 SHALL 基于 Agent 的历史任务数据，自动分析 Skill 工作流的执行效果，生成优化建议。企业主审核后可更新 Skill 配置。

#### Scenario: 品牌商务达人筛选 Skill 优化建议
- **WHEN** 系统分析品牌商务过去 50 次达人筛选任务的数据
- **THEN** 发现「大规模搜索阶段耗时过长」→生成优化建议：「增加粉丝量预过滤减少候选池」→推送 Dashboard 审核

#### Scenario: 企业主采纳 Skill 优化建议
- **WHEN** 企业主审核并批准 Skill 优化建议
- **THEN** 系统自动更新对应 Skill 的配置→记录 EvolutionLog→后续该 Agent 使用新版 Skill 流程

---

### Requirement: 反馈驱动进化

用户对 Agent 产出的每一次审核决策（批准/修改/拒绝）MUST 被记录并用于驱动 Agent 进化。反馈数据通过睡眠巩固转化为长期经验。

#### Scenario: 审核拒绝触发学习
- **WHEN** 企业主拒绝了品牌商务的邀约话术并标注原因「语气过于正式，不符合品牌调性」
- **THEN** 系统将拒绝原因+原始内容+修改方向写入短期记忆→睡眠巩固时提取模式→长期记忆中记录「该品牌偏好 casual 风格」

#### Scenario: 审核修改触发学习
- **WHEN** 企业主修改了内容运营的脚本并批准
- **THEN** 系统记录修改前后 diff→分析修改模式（如「增加了互动引导」「缩短了产品介绍」）→写入 Agent 偏好层

#### Scenario: 累积偏好自动生效
- **WHEN** 品牌商务 Agent 积累了 5 次以上关于「品牌调性偏好」的审核反馈
- **THEN** 系统在 Agent 执行新任务时自动注入该偏好作为上下文约束，减少后续修改次数
